# ADR-030: Entity identity, resolution, and merge: opaque ids, three-outcome resolver, same_as / different_from

## Status

Accepted

## Date

2026-09-14

## Context

The newspaper goal (ADR-028, ADR-029) has one hard requirement underneath everything else: the same person across fifty articles must stay one file. Today the substrate cannot promise that.

**What an entity id is today.** ARCHITECTURE.md § The atom envelope and the README's worked example both specify the `entity` field as an opaque multibase string (`z6MkrSarahChen001...`). `EntityId` in `crates/ffs-core/src/atom.rs` is an unconstrained `String`, so that intent was never enforced. Task_32 then made the practical choice that the projection filename should be readable and, because the id and the filename were the same thing, minted entity ids as display-name slugs in `slug_for_proposal` (`crates/ffs-daemon/src/dispatch.rs`), at accept time, with `from-<submission-id>` as the fallback. Two people named Sara Chen collide on `Sara_Chen`; a person who changes her name keeps the old id or gets a second one; a wrong guess by the scribe is baked into the identifier forever. This is Wikipedia's *page title* being used as Wikidata's *QID*.

**What the research found.** `docs/research/2026-09-14-entity-resolution.md` reviewed Wikipedia and Wikidata practice, the entity-linking literature (Bunescu and Pasca 2006 through BLINK 2020 and GENRE 2021), the record-linkage literature (Fellegi and Sunter 1969, Christen 2012, Bhattacharya and Getoor 2007), and industry identifier practice (W3C Reconciliation API, MusicBrainz, ORCID, Freebase). The findings that decide this ADR:

1. **Identity, names, and titles are three different things.** Wikidata's QID is opaque, permanent, and never reused; labels and aliases are non-unique data; the Wikipedia title is a changeable human string with parenthetical disambiguation and a redirect left behind on every move.
2. **Merges redirect, never delete, and undo restores both sides.** Wikidata: "Merged items should be redirected. Never reuse merged items for other things." ORCID is the cautionary case: the deprecated record's data is deleted and cannot be reinstated, so a wrong merge is unrecoverable.
3. **Two human assertions bracket the automation.** P460 "said to be the same as" records a suspicion without merging; P1889 "different from" records a confirmed non-duplicate so nobody merges the pair again. The second is the human-override rule the agent memory convention (ADR-027) already requires.
4. **Notability is a NIL policy.** Wikipedia covers the event, not the one-time person. A single passing mention does not mint an identity.
5. **Fellegi and Sunter: two thresholds, three outcomes.** Above the upper threshold is a match, below the lower is a non-match, and the band between goes to clerical review. Every mature system, from Splink to the W3C Reconciliation API's `match` flag, implements this rule.
6. **The entity-linking pipeline is fixed in shape.** Candidate generation from an alias table with prior probabilities, disambiguation by context and by coherence with the other mentions in the same document (AIDA showed coherence is the strongest signal), an explicit NIL decision, and NIL clustering so unlinked mentions still share identity across documents. The neural era replaced the scorers, not the shape.
7. **Cluster ids are separate from record ids** in every ER system because merges and splits happen. If the id is the name, every rename, merge, or split rewrites references.

FFS already has most of the machinery these findings ask for: atoms about an entity id, supersession chains that keep history, bitemporal validity, provenance on every claim, a quarantine that is the human gate, `aliases[]` planned on `person.generic` v2 (ADR-028), daemon-side resolution with a `resolution` field (task_36 as amended), the additive/conflict rule (ADR-029), an FTS5 `search_fts` in the store trait that nothing exposes yet, and wikilinks that resolve by file basename. What is missing is the identity discipline and the resolver.

## Decision

FFS separates identity from name from filename, adopts the Fellegi-Sunter three-outcome rule with the quarantine as the review band, and makes merges reversible signed atoms. Seven parts.

### (1) Entity ids are opaque and permanent

- A new entity id is 16 random bytes encoded as base58btc multibase (the `z` prefix, consistent with the encodings in ADR-018). It carries no meaning and is never derived from a name, a title, a URL, or a submission id.
- The daemon mints the id when a proposal resolves to `new`, at the moment of acceptance or auto-acceptance (ADR-029), inside the same signing path. Proposals in the quarantine carry no id until then, except when they resolve to an existing entity.
- Existing slug ids (`Sara_Chen`, `note-2026-06-21-0912`) stay valid forever. An id is an arbitrary string; nothing is migrated; the materializer and every reader treat a slug id exactly like an opaque one. New ids are simply never minted that way again.
- Article entity ids (task_40) are also opaque; the URL is the dedup key, not the id.

### (2) Human-readable filenames are a projection concern

The materializer, not the id, owns readability:

- The basename is derived from the head atom's `display_name` (or `title`) at render time, slugified as today.
- On a basename collision within a family, the file gets a Wikipedia-style parenthetical qualifier taken from the head's `organization` first, then `role`, then the `valid_from` year: `Sara_Chen_(Acme).md`, `Sara_Chen_(City_Council).md`. This replaces ADR-028's family-token collision suffix; a qualifier a human recognizes beats a token nobody does.
- A persisted path-to-entity index (a small table in `store.db`, internal schema) maps every rendered path to its entity id, so `projection.render`, `ffs://` path addressing (ADR-006), and fast-path edits (ADR-014) resolve a path to an id without re-deriving the slug.
- On rename (a superseded `display_name`) or merge, the materializer moves the file and writes a one-line redirect stub at the old basename: `Moved to [[Sara_Chen_(Acme)|Sara Chen]]`. Existing wikilinks keep resolving. This is Wikipedia's redirect-on-move.
- Templates emit links as `[[target_basename|Display Name]]` and put `aliases:` in every projection's frontmatter, so Obsidian's link completion, search, and graph resolve any name to the one file.

### (3) A daemon-side resolver with three outcomes

The resolver runs in `crates/ffs-daemon/src/scribe.rs` on every multi-entity proposal set before it is enqueued (task_36):

- **Blocking.** Candidates come only from the same path family (people, orgs) and a normalized name key (case-folded, whitespace-collapsed, diacritics stripped, surname or organization core). Nothing outside the block is compared.
- **Candidate generation.** `entity.search` v2 (task_40) over `display_name` and `aliases[]`, ordered exact name, then alias, then prior count; plus `search_fts` over claim text for context evidence. Chains of `entity.same_as` are followed so a mention matching a losing alias lands on the winner.
- **Scoring.** Hand-set Fellegi-Sunter field weights (`log2(m/u)`) on agreement of `organization`, `role`, and `location` between the proposal and each candidate's head atoms, plus the prior. Organization agreement is strong evidence; a shared surname alone is weak. Weights and the two thresholds live in `$FFS_DATA_DIR/config/resolution.toml`, next to the predicate specs, hot-reloaded like them, with a starter file shipped by task_38.
- **Output per mention.** `resolution: existing | new | ambiguous` and `candidates: [{entity, score, matched_on}]`, where `matched_on` is one of `display_name`, `alias`, `context`. `existing` carries the winning entity id. `ambiguous` is emitted when the best score falls between the thresholds or when two candidates are within a margin of each other.
- **Whole-envelope input.** The resolver receives the entire multi-entity set for one submission, so an org proposal in the same article can raise a person candidate already affiliated with that org. Coherence scoring across mentions is a Phase 2 hook; the interface ships now.
- **`ambiguous` always routes to review**, regardless of any `Accept` grant. The review card is a reconciliation picker: the candidates with their `matched_on` evidence, a "someone new" option, and a "these are different people" button.

### (4) Merge and split as signed, reversible atoms

Two predicates, neither with a path family:

- **`entity.same_as`.** The atom's `entity` is the losing id; the claim is `{ target: <winning id>, reason, criterion }`; signed by whoever asserted it (the owner from the review UI; an agent only if a future grant allows). Readers, the materializer, and the resolver follow `same_as` chains. The losing entity's atoms stay exactly where they are and render under the winner's projection, so history is preserved and nothing is copied. Undo is supersession of the `same_as` atom with `valid_to = now`, which restores both sides with no data movement.
- **`entity.different_from`.** Symmetric: the claim is `{ other: <id>, criterion }`, signed by the owner. The resolver treats it as a hard block: no candidate that is `different_from` the proposal's resolved context is ever auto-linked, and the review UI never re-suggests a pair the owner has separated.
- On the losing entity's projection the materializer renders a single line, `Merged into [[...]]`, in place of the body.
- A **split** (a new entity plus supersessions moving specific atoms' `entity` to it, plus a `different_from`) is Phase 2.
- "Said to be the same as" needs no predicate: an `ambiguous` proposal sitting in the quarantine is the unresolved suspicion.

### (5) NIL policy: when to mint

- Always create the `source.article` and `event.business` records; they are append-only and cheap.
- Mint a `person.generic` entity on first mention only when the mention carries a distinguishing attribute (an organization or a role). A bare name with nothing else becomes an item in the article's `mentions[]` with `entity` unset, keyed for NIL clustering by normalized name plus the article's organization context.
- On the second qualifying sighting with the same NIL key, mint the entity and back-fill both mentions. Task_41's promotion rule (person.generic to contact.person after N articles) is the next rung of the same ladder.
- Organizations mint on first mention; an org named in the business press is distinguishing by itself.

### (6) Aliases and priors grow from use; human override is explicit

- When the owner accepts (or the substrate auto-accepts) a proposal whose mention text differs from the resolved entity's `display_name`, the mention text is appended to that entity's `aliases[]`. This is an additive-section edit, so ADR-029 may auto-file it.
- The prior for a surface form is the count of accepted resolutions to each entity, read from the store. A fresh substrate has no counts; the resolver falls back to most-recently-mentioned, then to review.
- `entity.different_from` is written only when the owner clicks "these are different people". It is never inferred from the owner picking one candidate over another, because the rejected candidates may be the same person seen from another angle.

### (7) Evaluation in the golden corpus

Every fixture in task_36's corpus carries an expected entity id (or `new`) per proposal. The scorer computes pairwise precision and recall over same-entity pairs and B-cubed over the resolved clusters, for the heuristic resolver in CI and for any LLM-assisted resolver out of band. Four identity fixtures are required: the same person across three articles with a nickname; two different people with the same name at different organizations; a rename announced in an article; a wrong merge and its undo.

## Alternatives Considered

### Alternative 1: Keep slug ids and add disambiguating suffixes

- **Description:** Keep `slug_for_proposal`; on collision append `_2`, an org token, or a year to the id itself.
- **Pros:** No new id format; ids stay typeable; nothing in the materializer changes.
- **Cons:** The id is still the title. A rename either leaves a misleading id or mints a second one; a merge has to pick which slug survives and rewrite every reference to the other; a split cannot be expressed at all. Wikipedia learned this and moved identity into Wikidata.
- **Why rejected:** Title-as-identity is the failure mode the research documents most thoroughly. Readability belongs to the filename, which this ADR keeps.

### Alternative 2: Sequential Q-style counters

- **Description:** Mint `Q1`, `Q2`, ... from a per-substrate counter, mirroring Wikidata.
- **Pros:** Short, opaque, memorable enough to type.
- **Cons:** Two federated substrates (ADR-007) both mint `Q17`; a pulled atom's entity id collides with a local one. Wikidata can use a counter because there is one Wikidata.
- **Why rejected:** Random 128-bit ids collide with negligible probability across any number of peers and need no coordination.

### Alternative 3: LLM-only resolution

- **Description:** Hand the article and the candidate projections to the `llm` engine (ADR-026) and let it decide identity.
- **Pros:** Highest ceiling; handles nicknames, transliterations, and context naturally.
- **Cons:** Nondeterministic, opt-in only, unavailable offline, and it produces a decision without a score the thresholds can act on.
- **Why rejected as the base:** The heuristic resolver with explicit weights must stand alone and be testable. An LLM or dense-retrieval reranker over the top candidates is allowed as a Phase 2 step behind the same opt-in as the extraction engine.

### Alternative 4: Infer `different_from` from review picks

- **Description:** When the owner picks candidate A over candidate B for a mention, record `A different_from B`.
- **Pros:** The block list grows for free.
- **Cons:** The owner chose the best match for one mention; they did not assert that A and B are distinct people. Inferring the negative poisons future resolution (memo § 6.8).
- **Why rejected:** Record only the positive (alias growth). Record the negative only on an explicit click.

## Consequences

### Positive

- One person, one file, across any number of articles, renames, and nicknames; the identifier never has to change.
- Merges are cheap to record and free to undo; no data moves; history is intact on both sides. This is strictly better than Wikidata's two-step restore and avoids ORCID's irreversible loss.
- The quarantine gets a precise job for identity: it is the Fellegi-Sunter review band, and every decision the owner makes there improves the resolver without any model training, because aliases and priors are read from the store.
- The additive/conflict rule (ADR-029) needs no special casing: `new` and `existing` proposals flow through it unchanged, and `ambiguous` is simply always conflicting.
- Federation is safer: opaque random ids do not collide across peers, and `same_as` is a signed atom a peer can verify like any other.

### Negative

- The path-to-entity index is new state the materializer must keep consistent with the store; a crash between insert and index write needs a rebuild path (re-render everything from heads, which is already idempotent per task_25).
- Opaque ids in `ffs://<graph>/entity/<id>` URLs are not typeable. Path addressing (`ffs://<graph>/people/by-name/S/Sara_Chen_(Acme).md`) already exists and remains the human form.
- Two more predicates (`entity.same_as`, `entity.different_from`) and a resolver config file to document and keep stable.
- The heuristic resolver will be wrong sometimes. The thresholds start conservative (a wide review band), which means more cards for the owner until the corpus scores justify narrowing them.

### Risks

- **Slug and opaque ids coexist forever.** Readers that assumed the id was a name (the plugin's `openHit` slugging, `path_for_entity`) break on opaque ids. Mitigation: task_38 routes every id-to-path lookup through the index and covers both id shapes in tests.
- **Wikilink churn on collision.** When a second Sara Chen appears, the first one's file is renamed to add a qualifier and every existing `[[Sara_Chen]]` link now hits the redirect stub. Mitigation: the stub resolves the link; the materializer may also rewrite links in files it owns (Phase 2, mirroring Wikidata's KrBot).
- **`same_as` across federated peers.** A peer's merge of two entities the local substrate also holds is not propagated in MVP. Recorded as later work; the atom shape is already federation-ready.
- **Alias growth pollutes.** A mis-resolved accept appends a wrong alias. Mitigation: aliases are additive claims with provenance; undo is supersession, and the corpus fixture for wrong-merge undo covers the path.

## Implementation Notes

- **Id minting** lives beside the signing path in `dispatch.rs` (the `sign_and_insert` helper task_39 extracts). `slug_for_proposal` is retired for entity ids and its slugify logic moves to the materializer for basenames.
- **`resolution.toml`** starter shape: a `[weights]` table with `organization`, `role`, `location`, `alias_exact`, `name_exact` as `m`/`u` pairs; a `[thresholds]` table with `link` and `new`; a `[blocking]` table with the name-key normalization options. Task_38 ships the file; task_36 reads it.
- **Resolver output** is carried on each proposal through quarantine storage (task_29 tables gain `resolution` and `candidates` JSON) and `ingest.list_pending`, so the plugin can render the picker.
- **`entity.same_as` and `entity.different_from`** are ordinary predicate specs under ADR-028 with no `[path]` table; their `claim_schema`s are three and two fields respectively. The store gains a helper `resolve_same_as(entity) -> entity` that follows chains with a cycle guard, used by `list_by_entity`, `head_of_chain`, the materializer, and the resolver.
- **Evaluation** extends task_36's scorer with pairwise and B-cubed metrics over expected entity ids; identity fixtures are listed in task_36 subtask 36.14.
- **Ownership across tasks:** task_38 mints opaque ids, builds the path index and redirect stubs, ships `resolution.toml` and the two predicates; task_36 implements the resolver, NIL policy, alias growth, and the corpus scorer; task_39 treats `ambiguous` as conflicting, renders the picker, writes `different_from` and `same_as` from the UI; task_40 makes `entity.search` v2 the candidate generator; task_41 reads role changes from affiliation supersession (ADR-031) rather than from name changes.
