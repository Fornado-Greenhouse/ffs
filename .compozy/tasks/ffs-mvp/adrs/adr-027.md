# ADR-027: Adopt the OKF Agent Memory Convention for agents using FFS as persistent memory

## Status

Accepted

## Date

2026-09-13

## Context

FFS is a memory substrate. Its thesis (ADR-001) is that knowledge should be records — signed, classified, bitemporal, capability-gated — rather than files. The MCP server (ADR-013) exists so that AI agents can read and write that substrate. The home-claw absorption scenario (ADR-004) is explicitly "many agents on personal hardware writing to and reading from the substrate."

What the substrate never said is **how an agent should behave** when it treats FFS as its memory. Three concrete gaps surfaced when the six MVP tools were read from an agent's point of view:

1. **`ffs_author_atom` reads like "save."** Its result is a `submission_id` for a proposal sitting in the ingest quarantine; nothing is persisted until the owner accepts it in the daily summary (task_19, task_29). The tool description did not say so. An agent that calls it and tells the user "I've saved that to your contacts" is making a persistence claim the substrate has not honored — and the quarantine, which is the AARM approval service (ARCHITECTURE.md § Security model), is precisely the thing that makes the claim false.
2. **Search-before-write was impossible over MCP.** The daemon has had `entity.search` since task_19, but no MCP tool exposed it. An agent could `ffs_query` an entity *by id* or render a projection *by path*, but could not ask "is there already a Sara Chen?" before proposing a new one. Duplication was the default outcome.
3. **No progressive-disclosure surface.** Projection listings (`path.list`) were reachable from the CLI and plugin but not from MCP. An agent wanting to orient itself had to guess paths or dump entity queries — the blanket-scan pattern that bloats context and leaks more than the task needs.

In parallel, [okf-memory/okf-agent-memory](https://github.com/okf-memory/okf-agent-memory) published a domain-neutral **Agent Memory Convention** (v0.1) over Google's Open Knowledge Format (OKF) v0.2. The format is markdown-with-frontmatter in a `knowledge/` directory; the convention is a behavioral contract for agents that use such a corpus as persistent memory. Its minimal agent contract:

- Persistent knowledge belongs in the corpus, not in the conversation.
- Search before creating; prefer updating existing knowledge over duplicating it.
- No blanket scans: index → search → inspect on demand → traverse only when needed.
- Preserve provenance; keep `generated` (by an agent) and `verified` (by a human) semantically distinct; never forge human verification.
- Preserve uncertainty: record "based on A and B, the agent infers C," not C as fact.
- Preserve meaningful history; do not silently overwrite.
- Human override: an explicit human correction wins and must not be silently re-inferred.
- Review knowledge after substantial work; do not manufacture low-value entries.
- Never claim persistence unless persistence actually succeeded.
- A three-tier governance model (`constraint` / `hold` / `context`) binds knowledge to code paths via `code_refs`, so an agent can ask "what governs this file?" before editing.

Almost all of that contract is *already enforced by FFS primitives* — the quarantine is the generated/verified boundary, provenance entries are `sources`, supersession chains are history, the daily summary is the review loop, capabilities are governance-as-data. What was missing was the behavioral layer that tells an agent how those primitives are meant to be used, and two small tool additions so the behavior is actually possible over MCP.

## Decision

FFS adopts the OKF Agent Memory Convention's **behavior**, mapped onto FFS primitives, in four parts.

### (a) Publish the FFS Agent Memory Convention

`docs/agent-memory/CONVENTION.md` is the behavioral contract for any agent (MCP-connected or filesystem-writing) that uses FFS as memory. It restates the okf-agent-memory contract in FFS terms:

| OKF Agent Memory concept | FFS primitive |
|---|---|
| `generated: { by, at }` | A proposal in the ingest quarantine, provenance-stamped with the agent identity (`mcp:agent/<id>` or the scribe's `ingest` entry) |
| `verified: [{ by: human:… }]` | The owner accepting the proposal; the resulting atom is signed by the owner key |
| `sources: [...]` | The atom's `provenance` array (`kind`, `uri`, `hash`) |
| `status` / `stale_after` | Bitemporal `valid_from` / `valid_to` plus supersession; nothing is deleted, heads move |
| Concept `type` | Predicate name, validated against the registered `claim_schema` |
| `index.md` / progressive disclosure | Projection listings (`contacts/by-name/S/`, `notes/recent/`) via `ffs_list_path`, then `ffs_render_projection` per entry |
| `okf search` | `ffs_search` (entity display-name / note-title match, capability-filtered) |
| `governance: constraint / hold / context` + `code_refs` | For the app: capability atoms (scope + actions) evaluated at the daemon boundary. For the repo: the ADR governance index (part d) |
| `log.md` | `tx_time` ordering, supersession chains, and the auditor's daily summary |
| Human override | Quarantine reject + owner-authored supersession; agents must not re-propose rejected content |

The substrate does **not** adopt the OKF file format. Atoms carry strictly richer, signed provenance than OKF frontmatter can express; projections remain the markdown surface (ADR-005), and an agent that prefers files can still drop OKF-shaped markdown into `ingest/` for the scribe to absorb.

### (b) Two additional MCP tools and one reworded tool

- **`ffs_search`** — translates to `entity.search` (`query`, optional `limit`, default 10, ceiling 50). Returns lightweight hits (`entity`, `predicate`, `display_name`), capability-filtered on the daemon side. This is the search-before-write primitive.
- **`ffs_list_path`** — translates to `path.list` (`path`, optional `page`). Returns a projection listing so an agent can orient by index instead of scanning.
- **`ffs_author_atom`** — same signature, reworded description: the result is a **proposal** with a `submission_id`; nothing is persisted until the owner accepts it; report the outcome as "proposed," never "saved"; search first; qualify inferences.

The MCP tool set becomes **eight** (nine since task_48 added `ffs_accept_proposal` for the owner-present morning read, ADR-035). Pre-1.0 this is an additive change; post-1.0 the eight signatures are the stable surface (ARCHITECTURE.md § Stability commitments). Catalog order is `ffs_query`, `ffs_search`, `ffs_list_path`, `ffs_render_projection`, `ffs_resolve_url`, `ffs_author_atom`, `ffs_inspect_predicate`, `ffs_audit_query`.

### (c) An instructional agent skill

`docs/agent-memory/skill/ffs-memory/SKILL.md` is a `SKILL.md`-shaped instruction bundle (name, description, workflow) that an MCP-aware agent host such as Claude Code can load. It is **not** a daemon-hosted skill bundle: it has no `entry_point`, is not discovered by `ffs-skills-host`, and is not installed under `$FFS_DATA_DIR/skills/`. It teaches the read-before-write loop, the proposal semantics of `ffs_author_atom`, and the end-of-task knowledge review.

### (d) Dogfood the practice in this repository

The repo's own persistent memory is `ARCHITECTURE.md`, the ADRs, and the task files. Two additions make the okf-agent-memory practice real here:

- **`.compozy/tasks/ffs-mvp/adrs/README.md`** — a governance index binding code paths to the ADRs that govern them, each with a tier (`constraint` / `hold` / `context`), plus a one-line description of every ADR. This is `code_refs` + `governance` applied to the ADR corpus without adopting a new file format.
- **`CLAUDE.md` § Knowledge discipline** — read the governing ADRs for a path before substantial work; search existing ADRs/tasks before proposing a new one; run the end-of-task knowledge review; never report a document as written unless it exists on disk.

## Alternatives Considered

### Alternative 1: Adopt the OKF bundle format wholesale as a `knowledge/` directory for the repo

- **Description:** Add `knowledge/` with OKF v0.2 concepts (`index.md`, `log.md`, typed concept files with `generated` / `verified` / `code_refs` frontmatter) and vendor or depend on the `okf` Go CLI for validation and search.
- **Pros:** Byte-for-byte compatible with the okf-agent-memory tooling; `okf search --for-path` works out of the box.
- **Cons:** The repo already has 27 ADRs, `ARCHITECTURE.md`, the PRD, the TechSpec, and 37 task files. A parallel corpus would restate them, drift from them, and violate the convention's own first rule — prefer existing knowledge over duplication. It would also add a fourth toolchain (Go) to a repo whose heterogeneity is already a stated trade-off (ARCHITECTURE.md § At a glance).
- **Why rejected:** The practices transfer without the format. The governance index and the CLAUDE.md section give the repo `code_refs` and the review loop at zero format cost.

### Alternative 2: Build BM25 full-text search over claim bodies now

- **Description:** Add an FTS5 virtual table (or an in-memory BM25 index like okf's) over atom claims so `ffs_search` matches note bodies and contact notes, not just display names and titles.
- **Pros:** Much closer to the okf search experience; catches "search before write" cases where the name differs but the content overlaps.
- **Cons:** New SQLite schema surface (internal, but non-trivial), new capability-filtering path over ranked results, and a new question — which claim fields are indexable per predicate — that belongs in the predicate spec (ADR-021) rather than hardcoded.
- **Why deferred:** `entity.search` on display name / note title is enough to make search-before-write *possible* for the MVP predicate set. Full-text search is recorded as an open question in the convention doc; it needs its own ADR once a predicate-spec field for indexability is designed.

### Alternative 3: Leave memory conventions to each agent's own prompt

- **Description:** Ship the two tools, skip the convention doc and skill; let Claude Code, OpenClaw, Hermes, etc. bring their own memory discipline.
- **Pros:** Least to write and maintain; no risk of the convention drifting from the code.
- **Cons:** The substrate's honesty guarantees — quarantine as human gate, provenance on every atom, no silent overwrite — are undermined the moment an agent tells its user "saved" about a proposal. That failure is not the agent host's to prevent; it is a property of how FFS's write path works, and FFS is the only party that can state it. The same holds for "don't re-propose what the owner rejected."
- **Why rejected:** The convention is where the substrate's write semantics become a contract agents can be held to. Tool descriptions carry the short form; the convention carries the reasoning.

## Consequences

### Positive

- An MCP agent can now do the full read-before-write loop over FFS: orient (`ffs_list_path`), search (`ffs_search`), inspect (`ffs_query` / `ffs_render_projection`), propose (`ffs_author_atom`), and report honestly ("proposed, pending your review").
- The generated/verified distinction that okf-agent-memory has to enforce by convention is enforced by construction in FFS (quarantine + owner signature). The convention doc makes that guarantee legible to agents and to people evaluating FFS against OKF-style tooling.
- The repo gains a path → governing-ADR index. "What decisions constrain `ffs-core::capability`?" becomes a table lookup instead of reading 27 ADRs.
- The convention is domain-neutral in the same way okf's is: nothing in it is contact-graph-specific, so the Phase 2 path families (decisions, projects, questions) inherit it unchanged.

### Negative

- Two more MCP tool signatures to hold stable post-1.0. ARCHITECTURE.md's stability list changes from "six" to "eight."
- Three documents (`CONVENTION.md`, the skill, the governance index) that can drift from the code. Tool descriptions are tested; prose is not.
- `ffs_search` is substring-on-name, not relevance-ranked. Agents used to BM25 search will find it blunt for large substrates.

### Risks

- **Convention drift.** The tool descriptions encode the short form of the convention and are covered by unit tests; the governance index is reviewed whenever an ADR is added (CLAUDE.md rule). Mitigation is process, not enforcement — acknowledged.
- **Agents ignore the tool description and still say "saved."** Mitigation: the `ffs_author_atom` result payload is a `submission_id`, not an atom hash; the skill and convention both tell the agent what that means. A stricter mitigation (returning `status: "proposed"` in the payload) is a daemon change and is noted in the convention's open questions.
- **Search surface too small to be useful.** If MVP usage shows agents duplicating entities because `entity.search` misses body-text matches, Alternative 2 gets its ADR.

## Implementation Notes

Implementation is scoped in task_37. Key mechanics:

- `crates/ffs-mcp/src/tools.rs` gains `ffs_search` and `ffs_list_path` translators plus `SEARCH_DEFAULT_LIMIT` / `SEARCH_MAX_LIMIT`; the catalog test asserts eight tools in the documented order; `tests/mcp_integration.rs` exercises `ffs_search` end to end against an in-process dispatcher.
- No daemon changes: both new tools forward to existing RPC methods (`entity.search`, `path.list`) that are already capability-filtered on the daemon side per ADR-013.
- `docs/agent-memory/CONVENTION.md` and `docs/agent-memory/skill/ffs-memory/SKILL.md` are prose; the skill has no `entry_point` so `ffs-skills-host` would skip it even if copied under `skills/`.
- `.compozy/tasks/ffs-mvp/adrs/README.md` is hand-maintained. Every future ADR that touches a path already in the index adds itself to that row; every ADR that introduces a new stable surface adds a row.
- README.md and ARCHITECTURE.md update the tool count and link the convention.
