# ADR-032: Review as markdown: the quarantine projected as an inbox file

## Status

Proposed (decided by spike task_44)

## Date

2026-09-14

## Context

The newspaper pipeline (tasks 38 to 45) produces 30 to 60 quarantine proposals on a normal morning: one `source.article` per item in the digest email, the people and organizations each article mentions, the affiliations and events the scribe infers, plus whatever the resolver could not settle and marked `ambiguous`. ADR-029 removes the additive majority from the owner's desk by auto-filing under an `Accept` grant, but what remains is still the hard part: role changes, ambiguous identities, merge candidates, and everything the scribe flagged with a parse warning. On a busy day that is ten to twenty decisions.

The only review surface today is the daily-summary panel in the Obsidian plugin (task_19, task_28). It was designed as a health-flag surface: five items maximum, sorted by priority, each with accept and reject. It is the right shape for "your federation bridge is unhealthy" and the wrong shape for "here are fourteen proposals, six of which need you to pick between two Sara Chens." A five-item panel does not scale to a queue, and a scrolling queue inside a sidebar pane is a poor editor for structured decisions. The plugin is also one editor among many: ADR-005 committed FFS to real files on disk so that any editor works, and a review flow that only exists inside the plugin re-creates the Obsidian lock-in ADR-005 rejected.

The substrate already has the pieces that a file-based review needs. The materializer writes projections from atoms and re-renders them on commit (task_25). The fast-path watcher (task_09, ADR-014) recognizes structured edits to projection files and turns them into daemon calls. The suppression registry (ARCHITECTURE.md concurrency rule 3) keeps the daemon's own writes from re-entering as user edits. The quarantine is persisted in SQLite (task_29) and exposes `ingest.list_pending`, `ingest.accept`, and `ingest.reject`. Nothing prevents the quarantine from being one more thing the daemon renders to disk and reads back.

## Decision

Proposed: the quarantine is also a projection. The daemon materializes `inbox/<YYYY-MM-DD>.md` in the vault root, one file per UTC day with pending proposals, and the fast path turns edits to that file into quarantine decisions.

### (1) The inbox file

`inbox/<YYYY-MM-DD>.md` is materialized by the daemon whenever the pending set changes. It carries frontmatter (`date`, `pending`, `decided`, `auto_filed`) and one section per pending proposal. Each section shows:

- the predicate and the resolved entity (or, for `ambiguous`, the candidates with `matched_on` and a one-line head summary each);
- the claim rendered the way the projection would render it, so the owner reads the record they are about to file, not JSON;
- provenance: source URI, engine and model per ADR-026, submission id;
- the decision block, a strict checkbox grammar the fast path parses.

The decision block for an ordinary proposal:

```
- [ ] accept
- [ ] reject
```

For an `ambiguous` proposal the block is a radio-style list: exactly one of the candidates or "someone new" may be ticked, plus an optional assertion that only takes effect together with a candidate pick.

```
- [ ] accept as Sara Chen (Acme)            <!-- entity: z... -->
- [ ] accept as Sara Chen (City Council)    <!-- entity: z... -->
- [ ] accept as someone new
- [ ] these are different people from: Sara Chen (City Council)
- [ ] reject
```

The entity ids ride in HTML comments so the visible text stays human and the parser stays exact.

### (2) The fast path reads decisions

The fast-path watcher recognizes `inbox/*.md` as a second file kind (after projections) and applies a new reverse-map edit kind, `inbox_decision`. A tick on `accept` calls `ingest.accept`; a tick on a candidate calls `ingest.accept` with `resolved_entity` set (task_39); a tick on "someone new" calls `ingest.accept` with `resolved_entity: "new"`; a tick on "these are different people" calls `entity.assert_different` (task_39) and requires a candidate tick in the same edit; a tick on `reject` calls `ingest.reject`. Two contradictory ticks in one section, or a malformed block, are a parse warning: the section is left pending, the warning is rendered into the file under the section, and the panel shows it as one of its five urgent items.

### (3) The daemon re-materializes after every decision

After the decisions are applied the daemon re-renders the file: decided sections collapse into a "Decided" list at the bottom (one line each, with the atom hash or the rejection), auto-filed items for the day appear in an "Auto-filed today" list with an `- [ ] undo` checkbox per item that calls `ingest.retract`, and merge candidates from the briefing (task_41) appear with `- [ ] merge` and `- [ ] keep separate` checkboxes. The write goes through the suppression registry so the watcher ignores the daemon's own re-render.

### (4) The panel keeps the five urgent items

The daily-summary panel is unchanged in shape: five flags, sorted by priority. It gains a count line ("14 pending, 6 need your eye") and a link that opens today's inbox file. It no longer needs to be the place where a queue is worked.

### (5) Spike task_44 decides

This ADR stays Proposed until spike task_44 puts one realistic morning (forty proposals, six ambiguous, three role changes) in front of the owner in both shapes. The outcomes are: accept this ADR and land it in task_39; reject it and keep the panel implementation task_39 already specifies; or a hybrid in which the inbox file handles the queue and the panel handles only the five urgent items. The hybrid is what this ADR proposes; the spike may narrow it.

## Alternatives Considered

### Alternative 1: A richer plugin-only panel

- **Description:** Grow the daily-summary panel into a paginated queue with a reconciliation picker, keyboard shortcuts, and bulk-select within a predicate.
- **Pros:** No new file kind for the fast path; the plugin already holds a client and knows the accept and reject calls; a richer UI can show candidates side by side.
- **Cons:** Review becomes an Obsidian-only feature, which is exactly the lock-in ADR-005 refused for reading and editing; a sidebar pane is a poor editor for fourteen structured decisions; every future review affordance (merge, retract, keep separate) is plugin code that Vim and VS Code users never get.
- **Why rejected (if spike 44 confirms markdown wins):** ADR-005's argument applies to review as much as to reading. It stays the fallback if the spike shows the file is worse to use.

### Alternative 2: A local web UI

- **Description:** The daemon serves a small review page on localhost; the panel and the CLI link to it.
- **Pros:** Any browser; richer widgets than markdown checkboxes.
- **Cons:** A new surface, a new process boundary, a new set of security questions for a daemon that today listens only on a UDS; nothing else in FFS is a web page.
- **Why rejected:** A fourth surface for one workflow is more than the workflow deserves, and it does not use the file-based strengths the substrate already has.

### Alternative 3: An email digest of pending proposals

- **Description:** The auditor mails the owner the pending list each morning.
- **Pros:** Zero UI work; reaches the owner wherever they read mail.
- **Cons:** No write path. Every decision still has to be made somewhere else.
- **Why rejected:** It is a notification, not a review surface.

## Consequences

### Positive

- Review works in any editor, on any device that syncs the vault, with no plugin. Ticking a checkbox on a phone in Obsidian Mobile is a valid accept.
- The inbox file is readable history: yesterday's file shows what was proposed, what was decided, and what was auto-filed, in one place, in the owner's own vault.
- The reconciliation picker, merge, keep-separate, and undo all become checkbox lines with the same parser, instead of four plugin widgets.
- The panel returns to the job it was designed for.

### Negative

- The fast path must understand a second file kind, with its own grammar, suppression handling, and re-render cycle. ADR-014 scoped the fast path to three edit kinds for a reason; this adds a fourth.
- The file is rewritten by the daemon after each decision. An owner mid-edit when a re-render lands sees the same class of race as concurrency rule 3 already handles for projections, and the suppression registry must cover inbox files too.
- Decisions are only as reliable as the checkbox parser. A tick on the wrong line files the wrong thing; the strict grammar and the contradictory-tick rule are the guard, not a cure.

### Risks

- **Checkbox parsing brittleness.** Editors reflow lists, change bullet characters, or auto-complete `[x]` differently. **Mitigation:** the grammar accepts `- [x]`, `- [X]`, and `* [x]`, matches on the comment-carried ids rather than visible text for candidate lines, and routes anything else to a parse warning in the panel rather than guessing.
- **The spike says no.** The owner finds the panel faster after all. **Mitigation:** task_39's panel implementation is fully specified already; this ADR is additive and its rejection costs nothing built.

## Implementation Notes

- Lands in task_39 if accepted: the `inbox_decision` edit kind and its parser live in `crates/ffs-fastpath/`, the inbox materialization in `crates/ffs-daemon/src/materializer.rs`, and the panel count line plus link in `obsidian-plugin/src/summary.ts`.
- The inbox is not a path family in the ADR-028 sense: it has no predicate, no entity, and no `[path]` table. It is a projection of quarantine state, rendered by a dedicated template.
- `max_per_day` for ADR-029's `Accept` grant should default to the sustained-review number spike 44 measures, so that what auto-files and what lands in the inbox add up to a morning the owner will actually do.
- The hybrid outcome keeps the panel's five urgent items and moves everything else to the file.
