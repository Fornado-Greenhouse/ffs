# ADR-029: Capability-gated auto-filing of additive proposals

## Status

Accepted

## Date

2026-09-14

## Context

The morning-newspaper goal (task_40, task_41) is a clerk that reads the local business press end to end and files what it finds — new companies, new people, role changes, deals — into the cabinet before the owner sits down. One Charlotte Business Journal digest yields 30 or more articles; at one or two proposals per article, that is 30 to 60 quarantine cards a day. Clicking accept on each of them is not "keeping the filing cabinet up to date," it is doing the clerk's job by hand with extra steps. Nobody will do it for a week.

But the quarantine is not incidental. It is the AARM **Approval Service** in FFS's security model (ARCHITECTURE.md § Security model): the human-in-the-loop fence between "an agent proposed this" and "the owner's key signed this." ARCHITECTURE.md lists the obvious shortcut as an anti-pattern in so many words: *"DON'T approve quarantined proposals in batches without per-item review. The approval is the human-in-the-loop fence."* ADR-027 built on the same fence: a proposal is "generated," an accepted atom is "verified," and the convention forbids an agent from claiming the second when only the first happened.

So the constraint is sharp. The fix must not weaken the fence. It has to make the fence **policy-as-data**, the way every other authorization decision in FFS already is (ADR-007: capabilities are atoms; the evaluator has no imperative policy code). And it has to distinguish the two kinds of filing a clerk does:

- **Additive filing.** A new folder for a company that did not have one. A new dated clipping in an existing person's folder. A new article record. Nothing that was true yesterday stops being true; the cabinet only grows.
- **Corrective filing.** "She is no longer VP at Acme; she is CEO at Beta." This *replaces* a fact. If the clerk is wrong — same-name confusion, a stale reprint, a misread — the cabinet now says something false and the old truth is buried under a supersession the owner never saw.

The convention already draws this line for agents: "never silently overwrite; supersession preserves history; the owner disambiguates conflicts" (ADR-027 § 14). What is missing is the substrate enforcing it at accept time, and a grant that lets the owner say *which* agent may file *which* predicates without review.

Two pieces of machinery this decision leans on already exist or are in flight:

- Predicate specs declare `additive_sections` in their `[rendering]` table (ADR-021; `crates/ffs-core/src/predicate/mod.rs`). The fast-path uses the same list to decide which edits are safe to apply without review (ADR-014). The quarantine can reuse it.
- Scribe v2 (ADR-026, task_36 as amended) tags each proposal with a `resolution` (`new` | `extends` | `conflicts`) against the entities it found via name lookup, and records engine + model in provenance.

## Decision

FFS adds a **capability-gated auto-filing** path to the quarantine, in five parts.

### (1) A new capability action: `Accept`

`ffs_core::capability::Action` gains an `Accept` variant. It is granted the ordinary way — a `capability.grant` atom signed by the owner, `entity` = the grantee's identity, `actions: ["accept"]`, `scope` restricted to predicates and optionally classifications — and evaluated by the same `capability::evaluate` that gates reads, writes, and federation pulls. No new policy code. Revocation is supersession, as for every other capability.

The grantee is the **submitting agent's identity**: the `mcp:agent/<id>` identity that `ffs_author_atom` stamps into provenance, or the ingest-folder writer's configured identity for filesystem drops (the courier from task_40). The daemon resolves the grantee from the submission's `source_uri` / provenance, never from the content.

The scope gains one optional dimension, `max_per_day: Option<u32>`: the ceiling on auto-accepted proposals per grant per UTC day. Absent means unlimited, which the CLI refuses to grant without an explicit `--unlimited` flag. The default the CLI prints and the first-use guide uses is 50 per grant, from spike task_44 (2026-09-20: 46 decisions reviewed in 7 minutes); the owner may raise it.

### (2) The additive rule

Holding an `Accept` grant is necessary but not sufficient. At enqueue time the quarantine classifies each proposal as **additive** or **conflicting**, and auto-accept fires only for additive proposals whose predicate the grant covers:

A proposal is **additive** iff one of:

- it creates a new entity (`resolution: new` from the scribe, confirmed by the daemon's own name lookup finding no head atoms for the slug), or
- it targets an existing entity and every claim field it sets is either (a) listed in the predicate spec's `additive_sections` (appends to `mentions[]`, `history[]`, `notes[]`, `tags[]`, `organizations[]`) or (b) currently unset on the entity's head atom, or
- it is a new record of a predicate whose spec marks the whole predicate append-only (`source.article`, `event.business` per ADR-028 — one record per article or event, never edited in place).

A proposal is **conflicting** iff any of:

- it would supersede a scalar field that already has a value on the head atom (`role`, `organization`, `title`, `location`, `display_name`, `status`, …), regardless of whether the new value differs;
- the scribe tagged it `resolution: conflicts` or attached a `parse-warning` / low-confidence rationale;
- the entity has a multi-leaf supersession head (ARCHITECTURE.md concurrency rule 1) — an already-ambiguous entity is never touched automatically;
- the grant's `max_per_day` is exhausted.

Conflicting proposals **always** route to review, exactly as today. This is AARM's Context-Dependent Allow with the context being *additive vs. conflicting*, and it is the convention's "never silently overwrite" rule (ADR-027 § 14) enforced by the substrate rather than requested of the agent.

### (3) Receipts: auto-accepted atoms carry the authorizing capability

Every atom produced by auto-accept carries an extra provenance entry `{ kind: "auto_accept", uri: "ffs://local/atom/<capability-hash>", hash: <capability-hash> }` naming the capability atom that authorized it. This mirrors invariant 7 for federation (the receiver records the atom *and* the capability hash that authorized its arrival). "Why is this in my cabinet?" is answerable from the atom alone: the clerk filed it, under this grant, from this article.

The submission itself moves to a new `SubmissionStatus::AutoAccepted` with `accepted_atom_hashes` populated, so `ingest.list_pending` is unchanged and the audit trail is preserved.

### (4) The daily summary shows what was filed, with undo

The auditor's daily summary (task_13) gains an **auto-filed** section: the count for the window, the entities touched (grouped by predicate), and per-item undo. Undo calls a new `ingest.retract` RPC that supersedes the auto-accepted atom with a copy carrying `valid_to = now` and provenance `kind: retraction` — history is preserved, the head moves back to the prior state (or the entity's folder simply goes empty for a new entity). Nothing is erased; erasure stays the separate structured operation the PRD reserves for it.

The Obsidian panel renders the section below the pending-proposal queue. The five-item cap on the panel's *flags* does not apply to the auto-filed list, which is a collapsible log, not a set of alarms.

### (5) Default off

A fresh substrate has no `Accept` grant. The owner grants one explicitly:

```
ffs capability grant --action accept --grantee mcp:agent/courier \
    --predicates source.article,event.business,org.company,person.generic \
    --max-per-day 200
```

The CLI gains a `capability` subcommand (`grant`, `list`, `revoke`) alongside `identity`, `predicate`, and `federation`. `revoke` authors a superseding capability with an empty action list; `list` shows active grants with their `max_per_day` and today's usage.

## Alternatives Considered

### Alternative 1: A "batch accept" button in the plugin

- **Description:** Add "accept all pending" to the daily-summary panel; the owner clicks once each morning.
- **Pros:** Trivial to build; no daemon changes; the owner is still nominally in the loop.
- **Cons:** It is the listed anti-pattern verbatim. There is no scoping — the button accepts a role change the same as a new article. There is no receipt — every atom is signed by the owner's key with nothing recording that no human looked at it. And it does not solve the problem: 30 cards nobody reads is still 30 cards, now accepted blind.
- **Why rejected:** Weakens the fence without making it policy. A button is code, not data.

### Alternative 2: Auto-accept everything from a trusted agent

- **Description:** An `Accept` grant means "whatever this agent proposes, file it."
- **Pros:** Simplest possible rule; the grant is still data and still revocable.
- **Cons:** Role changes, renamings, and mis-resolved entities overwrite silently. The supersession chain keeps the history, but the owner never sees the moment a wrong fact became the head — and the convention (ADR-027 § 14, § 15) says the owner resolves conflicts, not the agent.
- **Why rejected:** The additive/conflicting split is the whole point. Trust in the agent does not make a same-name collision less likely.

### Alternative 3: Confidence-threshold auto-accept from the LLM engine

- **Description:** The `llm` engine (ADR-026) emits a confidence score per proposal; the grant carries a threshold; proposals above it auto-accept.
- **Pros:** Adapts to extraction quality; a bad model files less.
- **Cons:** Model-reported confidence is not calibrated. Until task_36's golden-corpus scorer produces per-engine precision numbers, a threshold is a guess dressed as a policy. It also does not replace the additive rule — a 0.99-confident role change is still a corrective filing.
- **Why deferred:** Recorded as a future optional scope dimension (`min_confidence`) that can be added without touching the additive rule, once corpus scores exist to set it from.

## Consequences

### Positive

- The owner's morning changes from "accept 40 cards" to "skim what the clerk filed, glance at the 3 conflicts it held back." The fence still stands; it now stands only where it matters.
- Authorization stays uniform: one evaluator, one atom shape, one revocation mechanism. `ffs capability list` answers "what can file into my cabinet on its own?"
- Every auto-filed atom explains itself: the article it came from, the engine that read it, the grant that let it in.
- The additive/conflicting classifier is a pure function over proposal + head atoms + spec, so it is property-testable and reusable by the fast-path, which already draws the same line for editor edits (ADR-014).

### Negative

- `Action` gains a variant. The capability claim shape is a stable surface post-1.0; this ADR is the required record. Peers running older versions will not understand `accept` in a capability they pull — harmless, since `Accept` is never evaluated across federation, but the JSON must tolerate unknown actions (it does not today; task_39 fixes deserialization to skip unknown variants).
- Two new submission states and one new RPC (`ingest.retract`) widen the quarantine and the JSON-RPC method set.
- The classifier depends on task_36's `resolution` field for the "new entity" case. Until task_36 lands, the daemon's own name lookup is the only signal, and the heuristic engine's mis-resolution rate makes auto-filing new *people* risky. Task_39 depends on task_36 for this reason; auto-filing `source.article` and `event.business` records is safe earlier because they are append-only by spec.

### Risks

- **Flooding.** A misbehaving or compromised agent files hundreds of junk entities. **Mitigation:** `max_per_day` on the grant; the auditor's existing author-rate flag (priority 4, `audit.py`) already fires on per-agent write bursts; undo is one click per item and `ffs capability revoke` is one command for the lot. Anomaly-driven runtime deny remains Phase 2 (ARCHITECTURE.md § Acknowledged gaps).
- **Wrong "new entity" verdicts.** "Bob Smith" the banker and "Bob Smith" the developer become one folder, or one person becomes two. **Mitigation:** the classifier treats a slug collision with different `organization` as conflicting, not additive; task_36's entity-resolution hints improve the rest; the auditor's promotion/merge candidates (task_41) surface duplicates weekly.
- **The owner stops reading the auto-filed section.** The daily summary is then a log nobody reads and the fence is nominal. **Mitigation:** none in software. The section is designed to be skimmable (counts and names, not cards), and the conflicts it holds back are the alarms.

## Implementation Notes

Implementation is scoped in task_39. Key mechanics settled here:

- `Action::Accept` serializes as `"accept"`. `CapabilityScope` gains `max_per_day: Option<u32>` with `serde(default)`; `narrows_or_equals` treats a smaller or equal cap as narrowing and `None → Some` as narrowing.
- The classifier lives in `ffs-core::quarantine` as `fn classify(proposal, heads: &[AtomEnvelope], spec: &PredicateSpec) -> Filing { Additive, Conflicting(reason) }`. It reads `spec.rendering.additive_sections`; a predicate spec may additionally declare `[quarantine] append_only = true` (ADR-028's `source.article` and `event.business` set it).
- `ingest_submit` runs extraction as today; on `quarantine.complete`, the daemon evaluates `Accept` for the grantee against each proposal's target, classifies, and signs additive proposals through the **same code path as `ingest.accept`** (one writer task, same `AtomTemplate`, same `AtomCommitted` event so the materializer renders the file). Conflicting proposals stay `Extracted`.
- `max_per_day` usage is counted from the store (`auto_accept` provenance entries whose capability hash matches, `tx_time` within the UTC day), not from an in-memory counter, so it survives restarts.
- `ingest.retract { atom_hash }` is owner-only (`Supersede` capability on the target) and refuses atoms that are not heads.
- The daily summary claim gains `auto_filed: { count, by_predicate: {…}, items: [{ atom_hash, entity, predicate, source_uri }] }`; `audit.py` reads it from `health.summary`.
