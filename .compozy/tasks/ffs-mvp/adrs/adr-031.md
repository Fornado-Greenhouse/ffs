# ADR-031: Ontological alignment of the predicate set: roles as atoms, participants and mentions as entity references, optional BFO/CCO/IAO annotations

## Status

Accepted

## Date

2026-09-14

## Context

ADR-028 scoped the business-graph predicate set (`org.company`, `source.article`, `event.business`, `person.generic` v2) from the morning-briefing goal. It modelled a person's employer as a scalar `organization` field on the person, an event's parties as a flat list of names, and an article's mentions as a list of names. Before building it, the question "how does the same person across fifty articles stay one file" was researched on two tracks. Track 1 (entity resolution, `docs/research/2026-09-14-entity-resolution.md`) produced ADR-030. Track 2, this ADR, studied the ISO/IEC 21838 top-level ontologies to check whether the predicate shapes themselves are sound. The memo is `docs/research/2026-09-14-top-level-ontologies.md`; claims below are verified there unless marked otherwise.

**ISO/IEC 21838** (JTC 1/SC 32) has four parts: Part 1 (2021) is the requirements a top-level ontology must meet (a textual artefact with non-circular definitions, an OWL 2 axiomatization, a Common Logic axiomatization, documentation of conformance and coverage); Part 2 (2020/2021) is Basic Formal Ontology; Part 3 (2023) is DOLCE; Part 4 (2023) is TUpper. Conformance under Part 1 is a relation between ontologies (a domain ontology consistently extends the TLO); it is not a property a data system can claim.

**BFO 2020** splits everything into continuants (persist through time, keep their identity) and occurrents (unfold in time). A person is an object, an independent continuant. A role is a realizable, specifically dependent continuant: it has exactly one bearer, it exists because that bearer is in some social or institutional circumstance the bearer does not have to be in, and losing it does not change the bearer physically. A role therefore has a temporal extent that is not the bearer's. BFO has no Person or Organization class; the Common Core Ontologies (CCO, the mid-level suite under IEEE P3195 review) supply them and model exactly our pattern: `person 1 has role doctor role 1`, `doctor role 1 has organizational context healthcare organization 1`. Because OWL properties are binary and atemporal, CCO and the Industrial Ontologies Foundry represent the start and end of a role as `Gain of Role` and `Loss of Role` processes, and its holding as a `Stasis` process. An event is a process with participants; CCO distinguishes `agent in` (causally relevant) from `participates in`.

**TUpper** takes the "sideways" approach: a modular ontology built from PSL (processes, activity occurrences, fluents), mereotopology, time and units, from which the taxonomy is inferred rather than declared. It is first-order and process-first, the better fit for planning and precedence reasoning, the weaker fit for classifying things and attaching roles and documents to them.

**DOLCE** does not formalize roles at all; it classifies endurants by a concept at a time (`CF(x, y, t)`). Read against BFO, that is the same fact pattern encoded differently: a role is a relation between a bearer, a context, and a time, never a property stored on the bearer.

**IAO** defines an information content entity as a generically dependent continuant that `is about` some thing; a journal article is a `document`, concretized by one or more information bearing entities (the HTML page, the ingest markdown file). CCO's Information Entity Ontology adds that a name is a designative information content entity: "A person only has one name, but that name (content) can be found in many particular physical tokens." A name designates the person; it is not the person.

The recurring lesson across all three top-level ontologies: **a role is not an attribute of a person; an event has participants who play roles in it; a document is about entities, not about strings.** FFS's atom envelope already carries what OWL-based ontologies have to bolt on: `valid_from`/`valid_to` is the temporal region, and the supersession chain is the history. CCO's Gain/Stasis/Loss processes exist because OWL cannot say "this role held from 2024 to 2026"; an FFS atom says exactly that natively.

## Decision

Five parts. Parts (1) to (3) change the shapes ADR-028 specified; part (4) adds an annotation; part (5) records what is deliberately not adopted.

### (1) Affiliation is its own atom, not a field on the person

A new predicate `affiliation`. Its entity is the role particular itself (the BFO role instance), with an opaque id minted per ADR-030. The claim:

```toml
name = "affiliation"
version = 1

[claim_schema]
type = "object"
required = ["person", "organization"]

[claim_schema.properties]
person       = { type = "string" }   # entity id of the bearer
organization = { type = "string" }   # entity id of the organizational context
title        = { type = "string" }   # "CEO", "board member"
kind         = { type = "string", enum = ["employee", "executive", "board", "founder", "investor", "advisor", "member", "other"] }
source       = { type = "string" }   # article url or ffs:// atom
notes        = { type = "array", items = { type = "string" } }
```

The atom's `valid_from` is when the role began; `valid_to` is when it ended, `null` while current. A title change is a supersession. Two stints at the same organization are two role particulars, so they are two entities.

Rendering: `affiliation` declares no `[path]` family. Person templates gain an `## Affiliations` section and org templates a `## People` section, filled by a reverse lookup: the renderer calls `list_by_predicate(affiliation)` filtered on `claim.person` (for people) or `claim.organization` (for orgs), keeps the head of each chain at `as_of`, and passes the list into the Tera context as `affiliations`; those atoms join `source_atoms` in the projection response. Fast-path edits inside those sections cannot reverse-map through the person file to the affiliation atom, so they route to ingest as corrections, the path ADR-014 already takes for ambiguous edits.

`person.generic` v2 keeps `organization`, but its meaning changes: it is the current primary affiliation as a rendering convenience, mirroring the `organization` versus `organizations[]` split that `contact.person` already has. The scribe writes it, the briefing (task_41) may correct it, and it is never the record of roles over time.

Consequence for ADR-029, with no special casing: "Jane joined Acme" is a new affiliation atom, additive, and auto-files under an `Accept` grant; "Jane left Acme" or "Jane was promoted" supersedes an existing atom (setting `valid_to` or changing `title`), is conflicting, and routes to review. Gain of role is additive, loss of role is a supersession, and that is precisely the human-gate behavior the pipeline wants for role changes.

### (2) Events have participants with roles in the event

`event.business.parties[]` (a flat list of names) is replaced by `participants[]`:

```toml
participants = { type = "array", items = { type = "object", properties = {
  entity  = { type = "string" },   # resolved entity id; absent while unresolved
  display = { type = "string" },   # the name as printed; always present
  role    = { type = "string", enum = ["acquirer", "target", "investor", "investee", "hire", "employer", "departing", "landlord", "tenant", "developer", "winner", "partner", "other"] }
}, required = ["display"] } }
```

`date` is the event's temporal region: `valid_from = valid_to = date` for a point event; a range for a process with duration. `kind` (from ADR-028) names the process type. Templates emit `[[<target>|<display>]]` for each participant that has an `entity`, and plain `display` otherwise.

### (3) Articles are about entities; the URL is the bearer

`source.article.mentions[]` becomes an `is about` list of `{entity, display, context}` items: `display` is the designator as printed, `entity` the referent once resolved, `context` the one-line role context the courier supplied. Storing names alone would make "everything about Jane" a string match forever; this is the same finding track 1 reached from the resolution side.

`source.article` gains `content_hash` (BLAKE3 multihash of the fetched page, when the courier supplies it). The normalized `url` is the information-bearer key: a re-fetch is a new bearer of the same content and MUST resolve to the same article entity. That gives task_40's URL dedup its ontological reason. `summary` remains an agent-authored descriptive content entity about the article, which is why the agent memory convention's "mark inferences as inferences" rule (ADR-027) applies to it.

### (4) Predicate specs may carry an informative `[ontology]` table

```toml
[ontology]
bfo  = "role"                  # continuant | occurrent | object | object aggregate | role | quality | information content entity | process
cco  = "cco:OccupationRole"    # optional mid-level class
iao  = ""                      # optional, for documents
note = "bearer = claim.person, context = claim.organization, temporal region = valid_from..valid_to"
```

The table is optional, informative, never validated beyond TOML shape, and never reasoned over. The loader accepts it (it has to be declared because `RawSpec` is `deny_unknown_fields`) and ignores unknown values. The mapping for every predicate lives in `docs/ontology-alignment.md`, which also defines the vocabulary of the `bfo` field. What it buys: design discipline (asking "is this a thing, a role, an event, or a document" is the single question that would have caught `organization` as a scalar before it was written); a basis for federation vocabulary agreement later (two substrates that both say `affiliation` is a BFO role with a bearer and a context can map each other's predicates even if field names differ, which ADR-007's bilateral federation has no mechanism for today); and a cheap path to RDF/OWL export later.

### (5) What is not adopted

- No OWL reasoning in the substrate. Part 1's own introduction positions OWL 2 as the decidable language for ontology quality assurance; FFS's runtime questions are lookups.
- No class hierarchies. `predicate` is the type, flat. CCO's deep trees exist for cross-agency data integration; a four-drawer personal substrate gains nothing from them.
- No temporalized relations and no Gain/Loss/Stasis process atoms. Those exist because OWL properties are binary and atemporal; the FFS atom is the temporal region.
- No requirement that a role be realized in a recorded process. BFO says roles are of types some instances of which are realized; storing the role does not require storing the realization.
- No claim of ISO/IEC 21838-1 conformance. Conformance is a relation between ontologies with dual OWL/CL axiomatizations and consistency proofs. Alignment annotations give the interoperability benefit at a small fraction of the cost.

## Alternatives Considered

### Alternative 1: `organization` as a scalar field on the person only (the ADR-028 shape)

- **Description:** Keep the person's employer and role as `organization` and `role` fields on `person.generic`; a change of job supersedes the person atom.
- **Pros:** One predicate, one template, the wikilink is a one-liner.
- **Cons:** Head selection in FFS is unique per `(entity, predicate, as_of)`; two concurrent affiliations (a founder who also sits on a board) either overwrite each other or surface as a multi-leaf conflict. "Who was CEO of Acme in 2024" becomes a scan over every person's superseded claims. Under ADR-029, a person atom that already has an `organization` makes "Jane left Acme" look like a scalar supersession (correct) but makes "Jane also joined a board" look like one too (wrong: it is additive), so the policy would need special cases.
- **Why rejected:** The ontology's one-bearer-many-roles is the normal case, not the edge case; the shape has to make concurrency ordinary.

### Alternative 2: A relationship predicate keyed on the person

- **Description:** `person.affiliations` as a predicate whose entity is the person and whose claim is a list of affiliations.
- **Pros:** No new entities to mint; the person file renders its own roles with no reverse lookup.
- **Cons:** Same head-uniqueness problem in a different coat: every affiliation change supersedes the whole list, so a gain of role and a loss of role are both supersessions and ADR-029 cannot tell them apart. Two articles on the same day about two different roles produce a multi-leaf head. Nothing can be shared or federated at the granularity of one role.
- **Why rejected:** It loses the additive-versus-conflict distinction that makes auto-filing safe.

### Alternative 3: Adopt CCO wholesale

- **Description:** Import CCO's Agent, Event, Information Entity, and Time ontologies as the predicate vocabulary, with `Gain of Role` and `Stasis of Role` atoms.
- **Pros:** Maximum interoperability with the DoD/IC data ecosystem CCO serves; every modelling question already answered.
- **Cons:** Cross-agency integration machinery: deep class trees, temporalized process patterns that exist only because OWL lacks temporal extents, and a vocabulary far larger than four drawers need. The substrate's readable-projection thesis (ADR-005) suffers when a hire is three process atoms and a role atom.
- **Why rejected:** Take the categories and the discipline, not the machinery. The `[ontology]` annotation keeps the door open.

## Consequences

### Positive

- Concurrent roles, role history, and "who held this role when" become ordinary bitemporal queries over one predicate.
- ADR-029's additive/conflict rule handles gain and loss of role with no special casing.
- Mentions and participants carry entity references, so track 1's resolution work (ADR-030) has somewhere to land its results and "everything about Jane" stops being a string match.
- Predicate specs answer "what kind of thing is this" in one line, which is the cheapest interoperability investment available and the one that catches modelling errors earliest.

### Negative

- One more predicate to maintain, and the renderer gains a reverse lookup (a `list_by_predicate` filter on a claim field; cheap at personal scale, but the first place the renderer reads atoms not about the entity being rendered).
- The scribe must resolve two entities (person and organization) before it can emit one affiliation proposal, so affiliations are the proposals most likely to land as `ambiguous` under ADR-030's thresholds.
- `event.business` and `source.article` become slightly harder to author by hand (objects in arrays); the ingest contract in task_40 keeps the courier's markdown simple and lets the scribe build the objects.

### Risks

- **Federation skew.** A peer that has not registered `affiliation` receives affiliation atoms in a pull. The store does not consult the registry at insert, and neither does the federation pull path (verified: only `predicate.inspect` and the renderer call `registry.get`), so the atoms are stored and signed like any other; the materializer skips atoms whose predicate has no family, and a render request for an unknown predicate returns `UnknownPredicate`. The peer sees nothing until it registers the spec, and loses nothing. **Mitigation:** the starter spec ships with the installer; the `[ontology]` note tells a peer what the predicate means before they map it.
- **Reverse-lookup cost grows with affiliation count.** At the 10K to 100K atom envelope it is a single predicate scan with a claim-field filter. **Mitigation:** add a `(predicate, claim.person)` index to the SQLite schema if the render budget (500 ms) is threatened; ADR-016 leaves the schema internal.
- **Annotation drift.** `[ontology]` values could rot as specs evolve. **Mitigation:** `docs/ontology-alignment.md` is reviewed whenever a starter spec changes (a row in the governance index), and the values are informative, so drift misleads a reader but breaks nothing.

## Implementation Notes

Scoped in task_38 (the `affiliation`, `entity.same_as`, and `entity.different_from` starter specs, the two template sections and the reverse lookup, the `participants[]` and `mentions[]` object shapes, the `[ontology]` table in the loader and on every starter spec, `docs/ontology-alignment.md`), task_36 (the scribe emits affiliation proposals beside person and org proposals and fills `entity` in mentions and participants from resolution), task_40 (`content_hash` and the URL-as-bearer dedup rule), and task_41 (role changes are detected from affiliation supersession, not from person scalar supersession). Nothing changes in ADR-029.

The `[ontology]` vocabulary for `bfo` is deliberately the small set of BFO categories a predicate author can answer without reading the standard: `continuant`, `occurrent`, `object`, `object aggregate`, `role`, `quality`, `information content entity`, `process`. Starter mapping: `contact.person` and `person.generic` are `object` (CCO Person); `org.company` is `object aggregate` (CCO Organization); `affiliation` is `role` (CCO OccupationRole); `event.business` is `process` (CCO Event, participants via `participates in`); `source.article` and `note` are `information content entity` (IAO document); `capability.grant` is `information content entity` (a prescriptive one); `entity.same_as` and `entity.different_from` are `information content entity` (designative assertions about identity, per ADR-030).
