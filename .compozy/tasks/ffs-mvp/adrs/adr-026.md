# ADR-026: Scribe v2 — predicate-schema-driven extraction with pluggable engines

## Status

Accepted

## Date

2026-06-21

## Context

The scribe skill (task_11, refined in task_32) extracts structured proposals from free-text notes dropped into `ingest/`. Its extraction logic is regex heuristics: a `[A-Z][a-z]+\s+[A-Z][a-z]+` bigram scan for names, pattern detectors for phones/emails, a stop-word list, venue masking. Live use on 2026-06-21 produced the canonical failure: a file named `Jon Jones.md` containing a key-value contact card (`Nickname: Bones / Occupation: UFC fighter / Phone numbe r- 9194284074`) was extracted as a `contact.person` with **`display_name: "Bones Occupation"`** — two random title-case words stitched across lines. Five distinct failure modes were catalogued (filename ignored, key-value card shape unrecognized, field labels treated as name candidates, no cross-check against the filename, verbatim typo propagation).

The deeper diagnosis: **this is not a regex-quality problem, it is an architecture problem.** Two structural facts make the current design wrong regardless of how clever the patterns get:

1. **Scribe ignores the predicate registry.** FFS predicates are defined in TOML specs carrying real JSON Schemas (`claim_schema` blocks) — the substrate already knows, in machine-readable form, exactly what shapes it can hold. The scribe hardcodes `contact.person` and `note` logic instead of consuming those schemas. Every new predicate the user registers is invisible to extraction until someone hand-writes new regexes.
2. **The quality ceiling of pattern-matching is far below what the substrate needs.** "Records-shaped substrate for personal knowledge" is the project thesis; the scribe is the front door through which records enter. A front door that guesses names from capitalized bigrams caps the entire system's usefulness.

The decision below resolves a question that blocked progress for roughly two months: which extraction technology, given the tension between quality (frontier LLM APIs), privacy (personal records leaving the machine), and operational weight (local model installs). The resolution came from noticing that **four of the five blocking sub-questions answer themselves from constraints already committed in this repository**:

| Blocking question | Answer, and where it was already decided |
|---|---|
| Is "records never leave the machine" a hard line? | Wrong framing. The distinction that matters is **ambient vs. invoked**. The substrate is SQLCipher-encrypted and local-first, but `ffs-mcp` (task_16) exists precisely so Claude can read the substrate when the user invokes it. A daemon that silently ships every note to an API is ambient exfiltration; a user-configured engine choice is invocation. Resolution: **local-only default, cloud backend as explicit opt-in configuration.** The blocker dissolves from a decision into a setting. |
| Extraction scope — contacts, or everything? | The predicate registry answers this. Extraction must target **whatever predicates are registered**, driven by their `claim_schema`s. Hardcoding any predicate shape is the bug being fixed, not a scope option. |
| Latency budget? | Non-issue. The ingest stability window (task_31, 30 s) plus the asynchronous quarantine mean extraction latency is invisible below ~30 s. Quality wins every latency tradeoff available. |
| Acceptable dependencies? | ADR-009 is decisive: skill bundles are **stdlib-only, zero pip dependencies**. This *eliminates* classical NER (spaCy/GLiNER require torch) and *selects* LLM-over-HTTP: both the Anthropic Messages API and a localhost Ollama server are plain JSON-over-HTTP, callable with `urllib.request` from the standard library. Python 3.11+ `tomllib` likewise reads the predicate TOMLs with zero deps. |
| Feedback/correction loop? | Already exists — the quarantine's accept/reject flow (tasks 19, 29). Record which engine+model produced each proposal in provenance; defer fine-tuning on accept/reject history to post-MVP. |

## Decision

Scribe v2 restructures extraction around two seams:

**1. Engine abstraction.** An `ExtractionEngine` interface inside the skill bundle (stdlib-only Python), with two implementations:

- **`heuristic`** — today's regex code, refactored behind the interface. Always available, fully offline, zero configuration. **Remains the default.**
- **`llm`** — a stdlib-`urllib` HTTP client with two thin backend adapters:
  - **Ollama** (`http://localhost:11434/api/chat`) — local models, nothing leaves the machine; for users who install Ollama.
  - **Anthropic Messages API** (`https://api.anthropic.com/v1/messages`) — highest quality ceiling; explicit opt-in; API key via environment or OS keychain.

  Selection via `FFS_SCRIBE_ENGINE` (`heuristic` | `llm`), backend via `FFS_SCRIBE_LLM_URL` + `FFS_SCRIBE_LLM_MODEL`. Any `llm` failure (network down, malformed output, schema-invalid JSON) falls back to `heuristic` so ingest never hard-fails on connectivity.

**2. Predicate-schema-driven prompts.** The extraction prompt is **generated from the registered predicate specs** — the skill reads the TOMLs from `$FFS_DATA_DIR/config/predicates/` via stdlib `tomllib` and renders each predicate's name, `claim_schema`, and description into the instruction. LLM output is validated against the same `claim_schema` before becoming a proposal. Consequences: adding a predicate extends extraction automatically; the schema is enforced at both ends; the heuristic engine remains the only place with per-predicate hand-written logic (and only as fallback).

Supporting decisions:

- **Provenance** on every proposal gains `engine` + `model` fields, surfaced in the quarantine review UI so the user can calibrate trust per engine.
- **A golden-corpus evaluation harness** (~20 fixture notes including the Jon Jones card, each with expected proposals) scores engines objectively via pytest. Heuristic-engine scores gate CI; LLM-engine scoring runs out-of-band (requires network/models). This converts "the scribe guessed wrong again" into a measured, regression-tested engineering surface.
- **The quarantine remains the human gate.** No proposal commits without user accept, regardless of engine.

## Alternatives Considered

### Alternative 1: Keep improving the heuristics (regex++)

- **Description:** Add filename consultation, key-value card detection, extended stop-lists, cross-checks — the five fixes catalogued from the Jon Jones failure.
- **Pros:** No new moving parts; fully offline; each fix is small.
- **Cons:** Two months of this produced "Bones Occupation." The ceiling is structurally low: every new note shape needs a new hand-written rule, and the registry-blindness is untouched. This is the bandaid path.
- **Why rejected as the strategy:** Retained only as (a) the default/fallback engine and (b) a bounded hygiene pass, because the heuristic engine still serves offline users. Rejected as the answer to extraction quality.

### Alternative 2: Classical NER (spaCy `en_core_web_trf`, GLiNER, NuExtract)

- **Description:** Pretrained token-classification models; ~92% F1 on standard entity types; ~100 ms on Apple Silicon; fully local.
- **Pros:** Fast, private, well-understood.
- **Cons:** **Violates ADR-009** — these require torch-class pip dependencies inside the skill bundle, or a sidecar model-server that is its own operational burden. Also structurally narrower than the requirement: NER tags entity spans; it does not fill arbitrary registered `claim_schema`s.
- **Why rejected:** The ADR-009 constraint alone is disqualifying; the scope mismatch seconds it.

### Alternative 3: Local LLM as the only engine (mandatory Ollama)

- **Description:** Require Ollama + a 5–15 GB model (e.g., Qwen 2.5 7B) on every install; all extraction runs locally through it.
- **Pros:** High quality and private, no cloud dependency.
- **Cons:** Forces a heavyweight install on every user of what is meant to be a light, technical-friend-installable substrate (ADR-005's friction-floor argument). Model supervision (updates, disk, RAM) becomes FFS's problem.
- **Why rejected as mandatory:** Accepted instead as one *backend* of the `llm` engine for users who choose it.

### Alternative 4: Cloud LLM as the only engine (Anthropic-only)

- **Description:** All extraction goes through the Anthropic API.
- **Pros:** Highest accuracy; simplest single path; the user already trusts Anthropic tooling with this repository.
- **Cons:** Ambient transmission of personal records to a third party as a *side effect of dropping a file in a folder* contradicts the local-first, encrypted-at-rest posture the whole substrate is built on. Also fails offline.
- **Why rejected as default:** Accepted as the opt-in backend with the strongest quality ceiling; rejected as ambient default.

## Consequences

### Positive

- Extraction quality ceiling moves from "regex bigram guessing" to "frontier LLM with schema-enforced output," at the user's chosen privacy level.
- The predicate registry becomes the single source of truth for extractable shapes — registering a predicate extends capture automatically.
- The eval corpus makes extraction quality measurable and regression-gated for the first time.
- ADR-009 is preserved: everything is stdlib (`urllib`, `json`, `tomllib`); no pip deps enter the bundle.
- Offline behavior is never worse than today (heuristic fallback on every `llm` failure).

### Negative

- Two engines to maintain; the heuristic engine cannot be deleted.
- LLM extraction is nondeterministic; the eval harness must score semantically (field-level comparisons with tolerance), not byte-exact.
- Prompt rendering from `claim_schema` couples prompt quality to schema quality — poorly-described predicates will extract poorly. (Arguably a feature: it pressures schema hygiene.)
- API-key handling adds a small secrets surface (mitigated: reuse the task_27/33 keychain machinery).

### Risks

- **Small local models may hallucinate fields.** Mitigation: schema validation rejects nonconforming output → heuristic fallback; quarantine catches the rest; eval corpus quantifies per-model reliability before recommending any model.
- **Anthropic API shape drift.** Mitigation: the adapter is ~50 lines of stdlib HTTP; version pinned via `anthropic-version` header; failures degrade to heuristic, never to ingest breakage.

## Implementation Notes

Implementation is scoped in task_36. Key mechanics settled here:

- Skill reads predicate TOMLs directly from `$FFS_DATA_DIR/config/predicates/` (stdlib `tomllib`) rather than extending the skills-host protocol — no daemon changes needed for schema access.
- Engine + backend config flows as environment variables through the existing daemon → skills-host → subprocess env path.
- Heuristic hygiene fixes from the Jon Jones postmortem (filename as name source, `^[A-Z][a-z]+:\s` card-shape detection, field-label stop-words) land as a bounded subtask because the heuristic remains the default engine — explicitly bounded so bandaiding ends here.
