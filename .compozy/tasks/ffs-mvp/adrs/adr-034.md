# ADR-034: Shared intake and shared accuracy over federation: articles as the queue, attestations as the quorum

## Status

Proposed (implements when ADR-033's deferral lifts; the local half may land earlier via task_46)

## Date

2026-09-14

## Context

The owner accepted ADR-033 (federation deferred behind the intake pipeline) with two statements that define what federation is for once it resumes:

> "We don't need every agent on earth reading the same news stories every day."

> "Ensuring it's accurate every day, like Wikipedia would: in any collection of N hosts, some percentage of N has to agree it's still accurate, at least one, preferably two or more."

The first is a work-distribution question: 5 to 20 peers each run a courier (task_40) against the same local business press. The second is a maintenance question: once a fact is filed, who confirms it is still true, and how many confirmations does it take. Three research memos under `docs/research/` answer them.

From `docs/research/2026-09-14-federated-feeds.md` (ActivityPub, AT Protocol, Nostr, Secure Scuttlebutt, Matrix, WebSub, IPFS):

- No protocol coordinates who reads first. Every one of them makes intake idempotent by a content key and deduplicates after the fact.
- Re-share is a reference, never a copy (ActivityPub `Announce`, gossipsub `IHAVE`, IPFS CIDs). FFS already has the fetch side, `GET /federation/v1/atom/<multihash>`.
- Articles have a natural cross-peer key and people do not. Atom's `atom:id` and RSS `guid` are the aggregator's newness test; normalized url plus `content_hash` is FFS's.
- Trust is a subscription to a signer, with opinions layered on by third parties (AT Protocol labelers, Nostr relay lists).
- The one missing FFS primitive is a per-(peer, predicate) subscription with its own watermark. Today a pull walks every predicate a capability covers with one watermark per peer and capability (`handle_pull_atoms` in `crates/ffs-federation/src/server.rs`, `tick_once_for_peer` in `scheduler.rs`).

From `docs/research/2026-09-14-agent-work-distribution.md` (Kafka, SQS, Pub/Sub, Cloud Tasks, etcd, Chubby, Contract Net, blackboards, A2A, MCP, CRDTs):

- Every production queue delivers at least once and pushes dedup onto a producer-supplied key whose memory outlives the message. "At-least-once plus idempotent consumer" is the default, not a compromise.
- Leases and leader election are advisory and justified only for expensive or side-effecting work.
- Federation pull already is the queue: predicate = topic, per-peer `tx_time` watermark = offset, capability atom = ACL, watermark advance after verification = commit, the 60-second heartbeat = polling.
- A peer's derived atoms must enter the local quarantine as proposals, never as local heads.
- Contract Net's announce step alone, without bidding, captures most of the coordination benefit.

From `docs/research/2026-09-14-shared-accuracy.md` (Wikipedia and Wikidata maintenance, truth discovery, Certificate Transparency, in-toto, reproducible builds):

- Wikipedia never lets a review state claim more than it checked. Pending-changes "accepted" means "checked for obvious problems"; verifiability, not truth, is the inclusion threshold; `{{As of}}` dates claims and schedules re-checks.
- Wikidata separates superseded-because-the-world-changed (normal rank with an end time) from deprecated-because-never-true (deprecated rank with a reason, P2241; disputes via P1310).
- Agreement counts only among independent sources (Dong et al. 2009 on copiers; Certificate Transparency's distinct-operator rule). Two peers who read the same article are one source.
- k-of-N is signatures plus counting, not consensus. Byzantine agreement is unnecessary among authenticated, trusted peers.
- Automated correction is precision-first and reversible (ClueBot NG: 0.1 percent false positives, one revert per day cap). Subtle staleness survives for months; the remedy is scheduled re-confirmation, not automatic change.

FFS already has most of the machinery: signed, content-addressed, immutable atoms with `valid_from` / `valid_to` and supersession; provenance on every atom, including engine and model (ADR-026); generated-versus-verified semantics (ADR-027); capability atoms as policy, including the `Accept` action (ADR-029); opaque entity ids and `entity.same_as` (ADR-030); `source.article` keyed by normalized url and `content_hash` (ADR-031, task_40); pull-based federation with watermarks (ADR-020, task_15). What is missing is one predicate, one spec table, one derived status, one subscription primitive, and the rule that a peer's reading arrives as proposals.

## Decision

Two halves. The local half needs no peer and lands with task_46. The federation half lands with task_47 when ADR-033's deferral lifts.

### Local half (task_46)

**(1) An `attestation` predicate.** An attestation is an atom about a fact. Its entity is the attested atom's content hash (multihash), not the entity-plus-predicate head. The hash is exact, and a superseded atom's attestations then belong to the historical claim it confirmed, which is what Wikidata's normal-rank-with-dates behavior wants; attesting "whatever is current" would silently re-point to a later claim nobody checked. Claim shape:

```toml
name = "attestation"
[claim_schema.properties]
as_of   = { type = "string" }   # ISO 8601 date the attester believes the fact held
basis   = { type = "string", enum = ["re_read_same_source", "independent_source", "primary_source", "owner_knowledge", "contradicted_by"] }
source  = { type = "string" }   # url, ffs:// atom, or "person:<name>" for owner knowledge
note    = { type = "string" }
```

Signed by the attester's key like any atom. No path family; attestations render inside the attested projection as a "Confirmed" line. The owner's acceptance of a proposal in the quarantine auto-emits one attestation: `basis = re_read_same_source` with `source` = the proposal's provenance uri when the owner read the proposal against its source, or `owner_knowledge` when the proposal carried no source. So k = 1 is met by the owner alone with no extra click. `basis = contradicted_by` is the dispute marker (see (3)); its `source` is the contradicting atom's hash. Relation to OKF: an attestation is one entry of OKF's `verified: [{by, at}]` list with two fields OKF lacks, `basis` and `source`, plus a signature; export to OKF is a projection of attestations onto `verified[]` (docs/agent-memory/CONVENTION.md § 12).

**(2) An `[attestation]` table in predicate specs.** The freshness horizon is a property of the kind of fact, so it lives next to the claim schema, git-versioned and hot-reloaded, not in capabilities (which answer "may this peer do X") and not in a separate policy atom.

```toml
[attestation]
k = 1                 # distinct independent attestations needed for "current"
window_days = 90      # attestation age after which the fact becomes "stale"
independent = true    # count distinct (basis, source) pairs, not distinct signers
```

Starter defaults: `affiliation` and `person.generic` k = 1, window 90; `org.company` k = 1, window 180; `source.article` and `event.business` no window (they record that something was published or happened, which does not go stale); `contact.person` and `note` no window (owner-authored). A per-substrate override in `$FFS_DATA_DIR/config/attestation.toml` may raise k. A missing table means k = 1, no window.

**(3) A derived status per head atom, computed at read time, never stored.**

| Status | Rule |
|---|---|
| **current** | at least k independent attestations within `window_days`, `valid_to` null or future, no open dispute |
| **unconfirmed** | accepted but fewer than k independent attestations ever |
| **stale** | the newest qualifying attestation is older than `window_days` |
| **disputed** | an attestation with `basis = contradicted_by` references this atom and no later attestation resolves it, or a contradicting head exists for the same entity and predicate via cross-peer `same_as` |
| **deprecated** | superseded by a correction whose reason is `never_true` |

Projections render the status in frontmatter (`status:`) and as an "as of" line, Wikipedia's `{{As of}}` made concrete: "as of 2026-06-21, confirmed by you (re-read) and Alice (independent)" on current facts, "[unconfirmed since 2026-03-01]" on the rest. The auditor counts each status per predicate. The briefing (task_41) gains a "Past their window" section listing facts whose window has elapsed ("14 affiliations last confirmed more than 90 days ago, 11 by you alone") with two actions: re-read the source (opens the article and records a fresh `re_read_same_source` attestation; uses the courier's fetch when enabled) and "unchanged" (records an `owner_knowledge` attestation). Neither is ever automatic.

**(4) A `correction` marker on supersession.** A superseding atom may carry provenance `kind: correction` with `reason: world_changed | never_true`. `world_changed` is Wikidata's normal rank with an end time: the old atom is history. `never_true` is Wikidata's deprecated rank with P2241: the old atom is `deprecated`, and its attestations are marked as confirming a claim later found false, which feeds source-reliability weighting later. `ingest.retract` (task_39) and the review surface expose the reason.

**(5) Nothing automatic ever changes an existing fact.** Staleness schedules re-confirmation; disputes route to review; corrections are signed by the owner. This is stricter than ClueBot's posture on purpose: the group is small and trusted, and the cost of a wrong automatic change to a personal record is higher than the cost of a stale one.

### Federation half (task_47)

**(6) Shared intake: `source.article` is the shared queue.** No leases, no leader. Every courier reads its own email on its own schedule and files what it finds; duplicates collapse on the article key. Mechanics:

- A per-(peer, predicate) subscription: a `federation_subscriptions` table keyed by `(peer, predicate)` with its own watermark, and a `predicates` filter on `GET /federation/v1/atoms`. The capability still bounds what the source serves; the subscription narrows what the consumer asks for. "From Alice I want `source.article` and `event.business`, not her contacts."
- Dedup after the fact by normalized url plus `content_hash`, with automatic `entity.same_as` for articles only. ADR-030 reserves `same_as` for the owner's click on people; for articles the key is exact, so the machine link is safe and stays undoable by supersession. The local reader sees one file, with the local summary as head and the peer's as a collapsed "also filed by" section.
- The courier checks pulled `source.article` keys before fetching (task_40's ledger consults pulled atoms as well as local ones) and, on a hit, records provenance `kind: federation, peer, atom` instead of fetching or extracting. This is ActivityPub's `Announce` and gossipsub's `IHAVE` in one; the reference is the atom hash and the fetch-on-demand endpoint already exists.
- A `courier.run` announce atom per run: `{ source, issue, article_keys, count, engine, model }`, signed by the peer, valid for the day. Peers that pull it before their own run may skip listed keys. This is Contract Net's announce without bidding, and it is the audit record the briefing needs ("courier ran, 23 articles, 2 peers also covered this issue").
- A `courier.claim` lease atom (TTL via `valid_to`, advisory, per issue) only if spike task_43 finds that full fetch is rate-limited, bot-walled, or paid. Otherwise not built.

**(7) The trust boundary.** A peer's `source.article` and `attestation` atoms may be pulled as atoms: they are records about a public document or about another atom, keyed exactly, and carry no claim about a local entity. A peer's derived atoms (`person.generic`, `org.company`, `affiliation`, `event.business`) arrive as proposals in the local quarantine with provenance `kind: federation` plus the peer's original engine and model provenance intact. They run through the local resolver (task_45) and ADR-029's additive rule under an `Accept` grant whose grantee is the peer's substrate key. "I trust Alice's reading of CBJ" is that grant, scoped to `source.article` and `event.business`; her people and orgs still meet the local resolver and the local human. Re-deriving with the local engine stays available as a per-peer setting and is not the default.

**(8) Shared accuracy.** Attestations federate like any atom. A new capability action `Attest`, mirroring `Accept`, says which peers may attest which predicates of mine; an attestation from a peer without the grant is stored (peer-version skew tolerance) but not counted. The quorum counts distinct independent sources: with `independent = true`, two peers who both attest from the same CBJ article (same `source` url or `content_hash`) are one confirmation; a second publication, a primary source (the company's own announcement, a filing), or owner knowledge is a second. Disputes (a peer's head for the same person, linked via cross-peer `same_as`, contradicts mine) route through ADR-029's conflict path to local review with a `contradicted_by` attestation recorded, never auto-resolved. Source-reliability weighting from past agreement (a peer's acceptance rate per predicate feeding the resolver) is later, after accept/reject history exists.

## Alternatives Considered

### Alternative 1: A broker or shared relay

- **Description:** A Kafka, NATS, or Nostr-style relay process that peers publish articles to and subscribe from.
- **Pros:** Familiar; push latency; one place to look.
- **Cons:** A new process to run, secure, and back up; a third party to every bilateral relationship; solves a problem 5 to 20 peers on a daily cadence do not have. The substrate is already the log and pull is already the relay.
- **Why rejected:** The memos are unanimous that the log plus idempotent consumers is the industry default; a broker adds surface without adding a guarantee FFS lacks.

### Alternative 2: Push delivery (WebSub, ActivityPub inbox)

- **Description:** Peers push new article atoms to subscribers' inboxes.
- **Pros:** Sub-minute latency; no polling.
- **Cons:** Requires a reachable endpoint per peer, retry queues, and a webhook surface to secure. ADR-020 chose pull for NAT and simplicity. The 60-second heartbeat is already two orders of magnitude faster than a daily courier.
- **Why rejected for now:** No cadence in the design needs it. If an agent-facing need appears, an MCP resource subscription on the article listing is the right place, not peer-to-peer push.

### Alternative 3: Byzantine agreement or a global reputation score

- **Description:** Run a consensus protocol over facts, or compute a network-wide trust score per peer.
- **Pros:** Formal guarantees; resistance to a malicious peer.
- **Cons:** Peers are authenticated by mTLS, pinned by fingerprint, and chosen by the owner. The guarantee wanted is accountability and freshness, which signatures plus counting provide (Certificate Transparency, in-toto). Global scores leak who reads whom and are meaningless in a group of 5 to 20.
- **Why rejected:** Trusted peers, exact keys, and signed attestations make consensus unnecessary; per-owner, per-predicate acceptance rates stay local and are enough.

### Alternative 4: Automatic reverts or automatic supersession on peer disagreement

- **Description:** When two peers disagree, let the majority or the most recent win automatically.
- **Pros:** Zero review load.
- **Cons:** ClueBot NG's precision-first, rate-limited posture is the ceiling for automated correction, and it exists for vandalism at Wikipedia's scale. A personal record changed automatically because a peer's scribe misread an article is exactly the failure the quarantine exists to prevent.
- **Why rejected:** Nothing automatic touches an existing fact. Disagreement is a review item.

### Alternative 5: Store a "reviewed" flag on atoms instead of deriving status

- **Description:** Add `reviewed: true` or `status: current` to the atom or the head record when the owner or a peer confirms it.
- **Pros:** Simple to render; no read-time computation.
- **Cons:** A stored flag drifts from the evidence: it does not expire, does not know about a later dispute, and claims more than was checked. Wikipedia's pending-changes lesson is that review state must mean exactly what was done.
- **Why rejected:** Status is a function of attestations, time, and supersession, so it cannot drift.

## Consequences

### Positive

- "Is it still accurate?" becomes a question the substrate answers, per fact, with evidence: who confirmed it, on what basis, from what source, when. The briefing turns that into a morning chore of bounded size.
- Shared intake costs no coordination. Two peers reading the same email pay one extra fetch and yield one `same_as`; the article log is shared, the cabinet stays yours.
- The trust boundary is unchanged across federation: the local owner's signature remains the only mark of "verified here"; a peer's reading is a grant the owner can revoke by supersession.
- The pieces are small: one predicate, one spec table, one derived function, one subscription table, one filter parameter, one capability action, one announce atom.

### Negative

- A new predicate that every head can be referenced by; attestation volume grows with every accept and every re-confirmation (roughly one attestation per accepted atom plus re-confirmations, well inside the envelope).
- Derived status is a read-time computation over attestations, `valid_to`, and supersession; renderers and the auditor pay for it on every render. Personal scale makes this cheap; it is a cost nonetheless.
- Window defaults (90, 180) are guesses until a few months of use say otherwise.
- The federation half cannot be validated until ADR-033 lifts and two substrates run.

### Risks

- **Attestation fatigue.** "Past their window" grows faster than the owner re-confirms and the section becomes noise. **Mitigation:** the "unchanged" bulk action is one click per batch; windows are per predicate and tunable; the auditor reports the backlog trend so the owner can widen a window rather than ignore the section.
- **Source dependence miscounted.** A peer attests from a syndicated copy of the same article under a different url, and the quorum counts two sources. **Mitigation:** `content_hash` catches identical bodies; the briefing shows the basis and source of each attestation so the owner can see "both from CBJ".
- **Peer proposals flood the quarantine.** A peer with a chatty scribe sends hundreds of people. **Mitigation:** the `Accept` grant's `max_per_day` (ADR-029) applies to peers as grantees; three-strikes damping per peer per entity is listed as later work in the shared-accuracy memo.
- **Article `same_as` links two different pages.** Two urls with the same normalized form but different content. **Mitigation:** `content_hash` disagreement blocks the automatic link and routes to review; the link is undoable by supersession.

## Implementation Notes

- task_46 (local half): `starter/predicates/attestation.toml` with an `[ontology]` annotation as an IAO information content entity about an atom; the `[attestation]` table in the spec loader (`RawSpec` is `deny_unknown_fields`, so the table must be declared) with defaults; auto-attestation in the accept and auto-accept signing path; a pure derived-status function in `ffs-core` with property tests; rendering in person, org, and affiliation templates; auditor counts and the briefing section; `correction.reason` on `ingest.retract` and in the review surface; `ffs attest <ffs://url> --basis ... --source ...`.
- task_47 (federation half): `federation_subscriptions` in `ffs-core::federation_peers` alongside the existing per-capability `watermarks`; a `predicates` parameter on `handle_pull_atoms`; `tick_once_for_peer` iterating subscriptions; article `same_as` on pull; the courier's pre-fetch check; `courier.run`; `Attest` in `capability::Action`; quorum independence across peers; dispute routing; peer-version-skew tests.
- Nothing in either half changes the atom envelope, the `ffs://` scheme, or the MCP tool signatures. `ffs_audit_query` and the briefing expose the derived status; no new MCP tool is required.
