# ADR-036: The daemon depends on the fast path, not the reverse

## Status

Accepted (2026-09-20, task_49)

## Date

2026-09-20

## Context

ADR-014 and ARCHITECTURE.md promise that an editor's save to a projection file becomes a supersession atom in under 200 ms, and ADR-032 promises that a tick in `inbox/<date>.md` applies as a quarantine decision. Task_09 built the watcher, the classifier, and the supersession path in `ffs-fastpath`, and task_39 built the strict checkbox parser and a `DispatcherSink` beside them. Neither ever ran in the production binary. `ffs-fastpath` depended on `ffs-daemon` for `Event` and `EventPublisher` (the notification broadcast the watcher publishes `ProjectionInvalidated` and `FastPathApplied` on) and, since task_39, for the `Dispatcher` behind the sink. A crate cannot depend on the crate that depends on it, so `main.rs` could not start the watcher, and `dispatch.rs` served `fastpath.submit` as a `task_09` stub. The in-process tests were green; the promise was not kept.

Two ways out were on the table.

**Invert the dependency.** Move the shared types down to `ffs-core` so the fast path depends only on the seams it uses, and let the daemon depend on the fast path. `Event` and `EventPublisher` are a `tokio::sync::broadcast` channel of JSON-RPC notification frames with no daemon-specific dependency; `SuppressionRegistry` already lived in `ffs-core`. The `DecisionSink` trait stays in `ffs-fastpath` (it is the fast path's seam), and the daemon implements it over its own `Dispatcher`.

**A sidecar binary.** A second process, `ffs-fastpath`, watching the vault and applying decisions over the UDS as a client. It avoids the type move but costs a second launchd job, a second Mach-O to sign and bundle under ADR-025, decisions applied over the socket instead of in-process, and a second suppression registry whose expected content hashes must agree with the daemon's, or daemon-induced writes re-enter as edits (concurrency rule 3).

## Decision

Invert the dependency. The crate graph is now:

```
ffs-core        (no workspace deps; owns Event, EventPublisher, SuppressionRegistry, PathIndex)
ffs-fastpath    depends on ffs-core
ffs-daemon      depends on ffs-core, ffs-fastpath, ffs-skills-host, ffs-federation
```

Concretely:

- `ffs_core::events` owns `Event`, `EventPublisher`, and the channel capacity. `ffs_daemon::notify` re-exports them so daemon code reads unchanged.
- `ffs_fastpath::inbox` keeps the parser, `InboxDecision`, `DecisionSink`, `apply_decisions`, and `decision_rpc` (the mapping from a decision to a JSON-RPC method and params). It gains `ParseWarning` and `INBOX_DIR`, which the daemon's inbox materializer imports.
- `ffs_daemon::DispatcherSink` implements `DecisionSink` in-process: it calls the dispatcher with `decision_rpc`'s method and params, records parse warnings on the inbox materializer, and on finish publishes `QuarantineChanged` and refreshes the inbox file.
- `main.rs` starts `FastPathWatcher` after the working-set and inbox materializers, on the data dir root, with the one `SuppressionRegistry` those materializers write to, and a `DispatcherSink` over the same `Dispatcher` the transport serves. The watched roots are the registry's projection families plus `inbox/`, decided per event by `is_watched_root`; dotfiles, `ingest/`, `run/`, `log/`, `skills/`, and `config/` are not the fast path's business. Startup logs the roots. Without a signing key the watcher is not started and a warning says so.
- `fastpath.submit` is implemented, not deleted: it runs the same `process_edit` the watcher runs, for the plugin's edit routing and for tests, and returns the fast path's `EditOutcome` (`ignored`, `applied` with the atom hash, `routed_to_ingest` with the submission path, or `inbox_decisions` with counts).

The sidecar is rejected. No stability-listed surface changes: the atom envelope, the `ffs://` scheme, the JSON-RPC method set (`fastpath.submit` was already listed), the MCP tool signatures, and the predicate-spec format are untouched.

## Consequences

- Editing a projection file in any editor produces a supersession atom in the production daemon; the binary e2e measured 89 ms from save to atom, inside the 200 ms budget, on the project lead's machine.
- Ticking a checkbox in today's inbox file commits the decision and the section moves under `## Decided` on the re-render.
- `ffs-fastpath` is now a library the daemon embeds, as the TechSpec's "embedded in daemon" always said. The TechSpec's build-order note that the fast path "calls dispatcher" is superseded: the fast path calls a `DecisionSink`, and the daemon provides the dispatcher behind it.
- The watcher's diff baseline is built from the head atom's frontmatter fields and additive sections, not from the full Tera template. The classifier compares structure (frontmatter pairs, section names, bullets), so the starter templates match today; a template that adds body text outside additive sections would route every edit to ingest. Plumbing the real `ProjectionRenderer` into the fast path is the follow-up if that happens.
- Two tests pin the shape: `crates/ffs-daemon/tests/fastpath_binary_task49.rs` (real binary, both promises) and `crates/ffs-fastpath/tests/watched_roots_task49.rs` (the watched set tracks the starter `[path]` tables).
