# ADR-028: Path families are declared in predicate specs; the business-graph predicate set

## Status

Accepted

## Date

2026-09-14

## Context

The goal that surfaced on 2026-09-13 is concrete: read the local business press end to end every morning, then keep the filing cabinet current on the movers and shakers — the people, the organizations they run or join, and the events (hires, deals, openings) that connect them. In FFS terms that is four drawers, and the substrate has three.

ADR-011 fixed the MVP path library at `contacts/`, `people/`, `notes/`. The implementation went further than the ADR: `crates/ffs-core/src/projection/path.rs` hardcodes a `PathFamily` enum with three variants, `PathFamily::try_parse` matches three literal strings, `PathFamily::primary_predicate` maps each variant to one predicate, and `family_for_predicate` reverse-maps exactly three predicate names. Every consumer inherits the constant: `projection/render.rs` calls `family.primary_predicate()` and `family.as_str()`; `ffs-daemon/src/materializer.rs` calls `family_for_predicate` and silently skips any atom whose predicate is not one of the three; `ffs-fastpath/src/watcher.rs` derives the predicate from the family; the Obsidian plugin carries its own copy as `PROJECTION_FAMILIES = ["contacts", "people", "notes"]` in `paths.ts` plus a `familyForPredicate` switch in `main.ts`; and `dispatch.rs::entity_search` hardcodes `"note" => "title"` to pick the name field.

The consequence: registering a predicate spec today gives you validation, rendering, and reverse-map rules, but no folder. An `org.company` atom would be signed, stored, and inspectable via `atom.get`, and would never appear on disk. The PRD's open question "path library extensibility for users" said the *mechanism* is committed (path-definition atoms) and the UX is open; nothing was built either way. Predicate specs, meanwhile, already carry a `[pagination]` table with `group_field = "display_name"` — the family's name field is implied but the family itself is not declared anywhere.

Two further facts shape the decision. `RawSpec` in `predicate/mod.rs` is `#[serde(deny_unknown_fields)]`, so any new top-level table has to be added to the loader explicitly — a spec cannot smuggle a family in ahead of the code. And the templates in `starter/templates/` render plain text (`organization: {{ claim.organization }}`), so even with four drawers Obsidian's graph view would show no edges between them.

## Decision

Three parts.

### (1) The predicate spec declares its path family

Predicate TOML gains a `[path]` table:

```toml
[path]
family = "orgs"              # folder root under $FFS_DATA_DIR
name_field = "display_name"  # claim field used for by-name grouping and search
```

`RawSpec` and `PredicateSpec` gain a `path: Option<PathSpec>`; the registry becomes the source of truth for families. `PathFamily` stops being a closed enum: `try_parse`, `primary_predicate`, `as_str`, `family_for_predicate`, and `path_for_entity` take the registry (or a `FamilyTable` snapshot derived from it) and resolve by lookup. `ParsedPath` carries the family as a resolved `PathFamily` value that wraps the folder name and its primary predicate. The renderer, materializer, fast-path watcher, and `entity.search` all read the family and name field from the spec; `entity.search` drops the hardcoded `"note" => "title"` match. The daemon exposes a `path.families` JSON-RPC method returning `[{family, predicate, name_field}]`, and the Obsidian plugin enumerates from it instead of from `PROJECTION_FAMILIES`.

`name_field` and `pagination.group_field` mean the same thing; a spec that declares both with different values is a load error. Specs without `[path]` remain valid and simply have no projection home (today's behavior for `capability.grant` and `auditor.daily_summary`).

The three starter specs declare their existing families (`contacts`, `people`, `notes`) so on-disk behavior is byte-identical after the change. The existing `path.rs` tests must pass unmodified against a registry loaded with the three starter specs.

### (2) The business-graph predicate set ships in `starter/`

| Predicate | Family | Shape |
|---|---|---|
| `org.company` (new, v1) | `orgs/` | `display_name` (required), `aliases[]`, `industry`, `location`, `website`, `description`, `notes[]`, `tags[]`, `history[]` |
| `source.article` (new, v1) | `articles/` | `title`, `url` (required), `publication`, `byline`, `published_at`, `summary`, `mentions[]`, `tags[]` |
| `event.business` (new, v1) | `events/` | `kind` (enum: `funding`, `acquisition`, `hire`, `departure`, `expansion`, `opening`, `closing`, `award`, `partnership`, `other`), `date`, `parties[]`, `amount`, `summary`, `source`, `tags[]` |
| `person.generic` (bumped to v2) | `people/` | existing fields plus `organization`, `aliases[]`, `mentions[]` (dated `YYYY-MM-DD: <what> (<article title>)` strings) |

**Why extend `person.generic` rather than add a fourth new predicate.** `contact.person` is for people you have a relationship with; it carries emails and phone numbers and its atoms are tier-classified for federation. The movers-and-shakers file is a different thing: people you read about, with a role, an organization, and a trail of dated mentions. That is exactly what ADR-011 said `people/` was for ("general person-entity references that aren't contacts"). Promoting a `person.generic` to a `contact.person` once you actually meet them stays a separate user action, as the PRD already notes; a later briefing feature surfaces the candidates.

**Articles store metadata, never full text.** A `source.article` atom holds title, URL, publication, byline, date, an agent-written summary, and the entities it mentions. It does not hold the article body. The URL is the provenance anchor; the publisher keeps the text. This keeps the substrate out of bulk-copy territory and keeps `articles/` readable as an index rather than an archive.

**Events are first-class because they are the edges with dates.** A hire connects a person and an org on a day; a funding round connects an org, its investors, and an amount. Folding events into `history[]` strings on the person and the org would lose the ability to list "what happened this week" — the morning-briefing query that motivates the whole set.

### (3) Templates emit Obsidian wikilinks

`organization` on a person renders as `[[<org_slug>]]`, `mentions[]` on an article and `parties[]` on an event render as `[[<entity_slug>]]`, and `source` on an event renders as `[[<article_slug>]]`. The slug is the entity id (task_32's human-readable form: display name with whitespace collapsed to `_`), which is also the projection filename. Obsidian resolves a bare `[[Acme_Corp]]` by basename anywhere in the vault, so the graph view becomes the business graph with no plugin work.

Basename resolution has a cost: two entities with the same slug in different families (`people/…/Mercury.md` and `orgs/…/Mercury.md`) are ambiguous to a bare wikilink. The rule: **entity slugs are unique across families.** The scribe's entity-id derivation (task_32, extended in task_36) checks the whole substrate, not just the target family, and disambiguates a collision by appending the family token (`Mercury_org`). The template always emits the bare slug; the collision rule lives in one place (id derivation) rather than in every template. Family-qualified links (`[[orgs/by-name/M/Mercury]]`) were rejected because they break when the materializer's layout changes and they read badly in the graph view.

## Alternatives Considered

### Alternative 1: Path-definition atoms (the PRD's committed mechanism)

- **Description:** A `path.definition` predicate; the user authors an atom declaring `family = "orgs"`, `predicate = "org.company"`, and the daemon builds the family table from those atoms.
- **Pros:** Families are substrate data — signed, supersedable, federatable. No spec edit needed to add a drawer.
- **Cons:** A predicate spec already is the git-versioned, hot-reloaded, human-edited declaration of "what this substrate holds"; putting the folder name in a different place than the schema, template, and reverse-map rules splits one concept across two mechanisms. Bootstrapping is awkward (an atom cannot exist before its predicate has a family to be listed under). Nobody has asked for per-substrate folders that differ from the spec.
- **Why rejected (for now):** One TOML line in the file that already defines the predicate is the lighter mechanism and covers the known need. Revisit if users want folders that vary per substrate without editing specs; the `[path]` table would then become the default a `path.definition` atom can override.

### Alternative 2: Extend the enum by hand

- **Description:** Add `Orgs`, `Articles`, `Events` variants to `PathFamily`, three more match arms everywhere, three more strings in the plugin.
- **Pros:** Smallest diff today.
- **Cons:** Repeats the bug that made this ADR necessary. The seventh family would need the same round of edits across five crates and the plugin, and a user-registered predicate would still have no folder.
- **Why rejected:** The fix has to be structural or it is not a fix.

### Alternative 3: A single `businesses/` family with a kind field

- **Description:** One predicate `business.record` with `kind ∈ {person, org, article, event}` and one folder.
- **Pros:** One spec, one template, one folder.
- **Cons:** One claim schema cannot validate four shapes cleanly; the reverse-map rules and the template would be a thicket of conditionals; listings would interleave people and articles; and `person.generic` would be duplicated rather than reused.
- **Why rejected:** The substrate's thesis is records with real schemas. Four shapes are four predicates.

## Consequences

### Positive

- Registering a predicate spec now yields a folder, listings, materialization, search, and plugin navigation with zero Rust or TypeScript changes. ADR-011's "Phase 2 families" (decisions, projects, questions, action-items, policies) become spec-authoring work.
- The morning-briefing pipeline has somewhere to file: an article in `articles/`, its people in `people/`, its orgs in `orgs/`, its events in `events/`, all wikilinked.
- Obsidian's graph view shows the business graph for free.
- `entity.search` and the plugin's search stop special-casing `note`.

### Negative

- The `[path]` table joins the TOML predicate-spec format under ARCHITECTURE.md § Stability commitments. It is small, but it is a public contract from here on.
- `PathFamily` changes from `Copy` enum to a registry-resolved value; every call site in `render.rs`, `materializer.rs`, `watcher.rs`, and `dispatch.rs` is touched. The materializer and fast-path watcher need a registry handle they did not previously hold.
- Four new templates and specs to maintain; `person.generic` gains three fields and three reverse-map rules.
- The plugin gains a startup RPC (`path.families`) and must handle the daemon being unreachable at load with a cached or empty family list.

### Risks

- **Version bump semantics.** `person.generic` moves from `version = 1` to `version = 2`. The loader parses `version` into `PredicateSpec.version` and nothing else reads it: the registry has no migration hook, `validate_claim` keys on predicate name only, and the reverse-map validator ignores it. Because the v2 change is purely additive (three optional fields), every existing `person.generic` atom still validates against the v2 schema and renders through the v2 template with the new sections suppressed when empty. The bump is therefore documentation of intent, not a migration. **Mitigation:** task_38 adds a loader test that a v1 claim validates under the v2 spec, and the starter README states that version bumps for additive changes require no migration while a breaking change (removed or retyped field) requires a new predicate name until a migration mechanism exists.
- **Slug collisions across families** surface only when the second entity arrives. **Mitigation:** the collision rule is enforced at id derivation and tested with a person and an org sharing a display name.
- **Hot-reload of a spec that changes its family** would strand materialized files under the old folder. **Mitigation:** treat a family rename as a breaking spec change (documented); the librarian's drift detector flags files under a family no spec declares.

## Implementation Notes

Scoped in task_38. Build order: loader (`[path]` on `RawSpec`/`PredicateSpec`, validation of `name_field` vs `group_field`) → registry family table → `path.rs` registry-backed → `render.rs`, `materializer.rs`, `watcher.rs`, `dispatch.rs::entity_search` → `path.families` RPC → plugin → starter specs and templates → docs. The three-family byte-identity check gates the switch from enum to lookup before any new spec lands.

Extraction into the new predicates is task_36's job (schema-driven prompts pick the specs up automatically); entity resolution against existing people and orgs is added to task_36 by the same amendment that references this ADR. The auto-filing policy that decides which of these proposals need a human is ADR-029 / task_39.
